# Этап 5. Первый сквозной запуск: экран поиска ходит в API

Это первый этап, где все слои сошлись в одной цепочке: ты вводишь логин, приложение берёт токен, спрашивает API, разбирает ответ и показывает его на втором экране. До сих пор у нас был красивый фундамент без дома, теперь по нему можно ходить.

>
> **Не пугайся вывода в тестах.** Тест «ошибка в нашем коде» нарочно бросает `StateError`, а экран в debug-режиме печатает его стек (`Непредвиденная ошибка: Bad state: баг`). Это ожидаемый шум, а не провал: рядом стоит `+115: All tests passed!`.

## 2. Граф зависимостей (DI)

```text
main()
 ├─ AppConfig            (из .env)
 ├─ TokenService(config, onLog)
 ├─ ApiClient(tokenService, onLog)
 ├─ UserRepository(apiClient)
 └─ SwiftyApp(repository) → SearchScreen(repository) → ProfileScreen(profile)
```

**Dependency Injection** (внедрение зависимостей) это громкое название простой вещи: объект не создаёт то, что ему нужно, а получает готовое снаружи. Почему так:

- **Один `TokenService` на всё приложение.** Это прямое требование задания «не создавать токен на каждый запрос». Если бы `SearchScreen` сам делал `TokenService(...)` в каждом нажатии, у нас было бы столько токенов, сколько нажатий. Создали один раз в `main`, передали вниз.
- **Тесты подставляют поддельный сервер.** `SearchScreen(repository: UserRepository(fake.api))`, и экран не знает, что сеть ненастоящая.
- **Экран ничего не знает про HTTP.** Он видит только `fetchUser(login)` и `ApiException`.

Альтернативы описаны в разделе 10.

## 3. Состояния экрана поиска

| Состояние | Поле | Кнопка | Под ними |
|---|---|---|---|
| Ожидание | активно | «Найти» | пусто |
| Ошибка ввода (`_fieldError`) | активно | «Найти» | красный текст под полем; **запрос не отправлялся** |
| Загрузка (`_loading`) | заблокировано | индикатор, не нажимается | пусто |
| Ошибка запроса (`_requestError`) | активно | «Найти» | баннер с значком |
| Успех | | | открыт экран профиля |

Разделение двух видов ошибок сделано сознательно. «Вы ввели `a b`» это ошибка пользователя, её место под полем. «Нет сети» это ошибка мира, ей место отдельным блоком. Смешаешь их в одну переменную, и текст «Нет сети» окажется красным под полем ввода, как будто логин кривой. Выглядит как баг, и проверяющий именно это заметит.

Ошибки очищаются, как только пользователь начал печатать (`onChanged`): старое «не найден» про `nobody` нелепо висит над уже набранным `nobody2`.

## 4. Пошаговая симуляция

Ввёл `  JDoe ` и нажал «Найти». Ход событий:

1. `_submit()` вызван. `_loading == false`, идём дальше.
2. `validateLogin('  JDoe ')` вернул `null` (после обрезки и приведения к нижнему регистру логин `jdoe` допустим).
3. `setState`: ошибки сброшены, `_loading = true`. Экран перерисован: индикатор вместо текста, поле и кнопка заблокированы.
4. `await repository.fetchUser('  JDoe ')`. Внутри: нормализация → `ApiClient.getJson(['v2','users','jdoe'])` → `TokenService.getToken()` (токена нет, идёт запрос `POST /oauth/token`) → `GET /v2/users/jdoe` с `Bearer`.
5. Пока всё это идёт, интерфейс **не замерзает**: `await` отдаёт управление, Flutter продолжает рисовать кадры (индикатор крутится).
6. Пришёл профиль. `if (!mounted) return;`: экран ещё в дереве.
7. `setState(_loading = false)`, затем `Navigator.push(ProfileScreen(profile))`.
8. Пользователь нажал «назад». Экран 1 на месте, кнопка снова «Найти», поле заполнено прежним текстом.

Сценарий «нет сети»: на шаге 4 `guardedRequest` бросает `NetworkException`, `catch` на `ApiException` кладёт её в `_requestError`, `_loading = false`, под кнопкой появляется баннер со значком `wifi_off`.

## 5. Ловушки `async` во Flutter

**5.1. `BuildContext` после `await`.** Пока запрос шёл, пользователь мог выйти с экрана. Тогда виджета уже нет в дереве, и вызов `setState` или `Navigator.of(context)` приведёт к исключению или тихой ерунде. Лекарство: `if (!mounted) return;` сразу после каждого `await`, перед обращением к `context` или `setState`. Анализатор даже ругается правилом `use_build_context_synchronously`, если забыть.

**5.2. Двойное нажатие.** Пока идёт запрос, пользователь нетерпеливо тычет по кнопке. Без защиты уйдёт десять запросов и откроется десять экранов профиля друг на друге (а в нашем случае ещё и упрёмся в лимит API). Защита двойная: `onPressed: null` в состоянии загрузки и проверка `if (_loading) return;` в начале `_submit` (клавиша «Поиск» на клавиатуре обходит кнопку, а вызывает ту же функцию).

**5.3. `catch (_)` как страховка.** Если в нашем коде баг (неожиданный `null`, `StateError`), без общей ловушки `_loading` остался бы `true` навсегда, и приложение вечно крутило бы индикатор. Поэтому есть последний `catch`, который показывает общее сообщение и сбрасывает `_loading`. В отладке он ещё и печатает стек, чтобы баг не прятался (подавлять исключения молча это хреновая практика, которая стоит часов отладки).

**5.4. Что `await Navigator.push` ждёт.** Он завершается, когда экран профиля закрыт. Нам это не мешает: после `push` в функции ничего не остаётся, но знай, что `_submit` формально «живёт» всё время, пока открыт профиль.

**5.5. Заблокированное поле теряет фокус и клавиатуру.** Это ожидаемое поведение: на время запроса клавиатура убирается. Если это раздражает, альтернатива: не блокировать поле, а только игнорировать повторные отправки.

## 6. Баннер ошибок и исчерпывающий `switch`

```dart
IconData get _icon => switch (error) {
      NetworkException() => Icons.wifi_off,
      AuthException() => Icons.lock_outline,
      NotFoundException() => Icons.person_off_outlined,
      RateLimitException() => Icons.hourglass_empty,
      ServerException() => Icons.cloud_off,
      UnexpectedResponseException() => Icons.error_outline,
    };
```

`ApiException` объявлен `sealed`, поэтому компилятор знает все его подклассы и **требует** покрыть каждый. Добавишь новый вид ошибки, и баннер перестанет компилироваться, пока не выберешь для него значок. Забыть про новую ошибку невозможно, и это ровно тот случай, ради которого sealed-классы придуманы.

Для `RateLimitException` с известным `retryAfter` к тексту дописывается «Повторить можно через N с.». Если заголовка нет, показываем общее сообщение без выдуманного времени.

Баннер завёрнут в `Semantics(liveRegion: true)`: программы чтения с экрана озвучат ошибку, когда она появится. Мелочь, но проверяющим нравятся такие штуки.

## 7. Журнал для отладки

В отладочной сборке в консоль (`flutter run`, вкладка Run в Android Studio) пишется:

```text
Получен токен, срок жизни 7200 с
GET /v2/users/jdoe → 200, 48213 байт, 912 мс
```

и при просроченном токене:

```text
GET /v2/users/jdoe → 401, 54 байт, 120 мс
Токен отвергнут сервером и сброшен
Получен токен, срок жизни 7200 с
GET /v2/users/jdoe → 200, 48213 байт, 880 мс
```

**Что туда НЕ попадает:** сам токен, `client_id`, `client_secret`. Это проверяет тест `logging_test.dart`. Журнал подключён через `kDebugMode`: в релизной сборке `onLog == null`, и вызовы ничего не делают.

Зачем он нужен: он закрывает сразу три открытых вопроса из предыдущих этапов (реальный `expires_in`, размер и скорость ответа профиля, не срабатывает ли таймаут 15 с). Поэтому в чек-листе ниже я прошу тебя прислать эти строки.

## 10. Альтернативы

| Подход | Плюс | Минус | Почему не выбрали |
|---|---|---|---|
| Передача зависимостей через конструкторы (наш) | Просто, видно глазами, легко тестировать | Длинная цепочка параметров при росте | Для двух экранов идеально |
| `InheritedWidget` / `provider` | Не нужно тащить параметры вниз | Лишняя библиотека и ещё одна абстракция для объяснения на защите | Преждевременно |
| `get_it` (service locator) | Доступ отовсюду | Скрытые зависимости, хуже тестируется | Магия, которую надо будет оправдывать |
| `FutureBuilder` вместо `_loading` | Меньше переменных состояния | Хуже с повторными попытками и ошибками ввода | Нам нужен контроль над кнопкой |
| `riverpod` / `bloc` | Масштабируется | Огромный перебор для двух экранов | Задание про основы мобильной разработки |
