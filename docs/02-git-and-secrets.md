## 1. Зачем это всё

Задание требует: учётные данные, API-ключи и переменные окружения хранятся **только локально в `.env`, а файл игнорируется git**. Если учётные данные оказываются в публичном доступе, проект **проваливается**. Проверяют люди, и смотрят они не только в текущие файлы, но и в **историю** репозитория.

Что именно считается секретом в нашем проекте:

| Значение | Что это | Можно в git? |
|---|---|---|
| `UID` | Идентификатор приложения в интре | **Нет** (хранить в `.env`) |
| `SECRET` | Секрет приложения в интре | **Нет**, самое чувствительное |
| `access_token` | Временный токен, который выдаёт API | **Нет**, и в логи тоже не выводить |

## 2. Теория: почему «просто удалить файл» не работает

Git хранит **всю историю**. Каждый коммит это неизменяемый снимок проекта, идентифицируемый хэшем. Если секрет хоть раз попал в какой-то коммит, то:

- удаление файла в следующем коммите убирает его только из **нового** состояния, а в старом коммите он остаётся;
- любой, кто склонирует репозиторий, получает всю историю, и секрет читается командой `git log -p` или просто открытием старого коммита на GitHub;
- если репозиторий публичный, секрет могли уже скопировать боты, которые сканируют GitHub постоянно.

Поэтому правило одно: **секрет не должен попасть в коммит ни разу.** Исправлять потом дороже и не всегда возможно (раздел 9). Правило `.env` в `.gitignore` мы добавили **до первого коммита**, пока в репозитории было пусто.

## 3. Как работает .gitignore

Файл `.gitignore` перечисляет шаблоны путей, которые git **не должен замечать**.

Две вещи, которые нужно знать:

1. **`.gitignore` действует только на неотслеживаемые файлы.** Если файл уже попал в индекс (был добавлен через `git add`), игнорирование его не снимет: git продолжит за ним следить. Чтобы перестать следить за файлом, но оставить его на диске, используют `git rm --cached <файл>`.
2. **Шаблон `.env` совпадает только с файлом (или папкой) с именем ровно `.env`.** Файлы `.env.local`, `.env.production` и подобные этим шаблоном **не игнорируются**.

Как проверить, игнорируется ли путь и каким правилом:

```bash
git check-ignore -v .env
```

Формат вывода: `<файл-правил>:<номер-строки>:<шаблон><TAB><путь>`. У нас:

```text
.gitignore:20:.env	.env
```

Это значит: файл `.env` игнорируется по правилу из `.gitignore`, строка 20. Если вывод **пустой**, правила нет и файл будет попадать в коммиты.

Проверка работает **даже если самого файла `.env` ещё нет**, и поэтому ею удобно пользоваться заранее.

| 2 | В пустой папке выполнена `flutter create ... .` (см. [01](01-environment.md#11-шаг-8-создание-проекта)) | Flutter создал и свой `.gitignore` |
| 3 | В `.gitignore` добавлена строка `.env` (в vim) | Строка 20 |
| 4 | `git status` до первого коммита | В индексе обнаружен лишний файл `.idea/.gitignore` |
| 5 | `git rm --cached .idea/.gitignore` | Файл убран из индекса, на диске остался |

| 8 | Первый коммит: «Initial Flutter project skeleton» | Хэш `2adb70c`, 27 файлов, 831 строка |
| 9 | `git push -u origin main` | Ветка `main` опубликована, отслеживает `origin/main` |
| 10 | Коммит `e4772bd`: создан `.env.example`, правило секретов вынесено в отдельный блок `# Secrets` | Хорошо, но при этом строка `.env` заменилась на `.env.*` (см. раздел 5) |
| 11 | Проверка `git check-ignore -v .env` показала пустой вывод | Обнаружено, что сам `.env` **не игнорируется**; секрета в репозитории ещё не было |
| 12 | Коммит `d9dfa2a`: строка `.env` возвращена | `.gitignore:22:.env`, проверено |

**Почему шаг 7 важен.** Вторая проверка `git status` после `git add .` позволяет **глазами** увидеть, что именно уйдёт в коммит, до того как оно станет историей. Привычка из двух команд (`git add .`, `git status`) окупается один раз, зато навсегда.

**Что осознанно попало в коммит:**

| Файл | Почему коммитим |
|---|---|
| `pubspec.lock` | Фиксирует точные версии зависимостей. Для **приложений** его принято коммитить, чтобы сборки были воспроизводимы |
| `.metadata` | Служебный файл Flutter, он так и задуман |
| `android/` (без `local.properties` и сборочных папок) | Нативная часть проекта нужна для сборки |

**Что не попало (и не должно):** `.dart_tool/`, `build/`, `.idea/`, `*.iml`, `android/local.properties` (последний содержит локальные пути и создаётся автоматически; Flutter-овский `.gitignore` его исключает).

## 5. Состояние .gitignore и рекомендации

Сначала правило `.env` стояло на 20-й строке внутри блока `# IntelliJ related`, рядом с `.idea/` и `*.iml`. Было два замечания, и оба затем применены:

1. **Блок не по смыслу.** `.env` это не про IntelliJ. Через полгода кто-то (в том числе ты), наводя порядок в «IntelliJ-блоке», может удалить строку вместе с остальными. Поэтому правила секретов вынесены в отдельный блок `# Secrets`.
2. **Только точное имя.** Шаблон `.env` не покрывает `.env.local`, `.env.production` и подобные. Поэтому добавлен шаблон `.env.*` с исключением для `.env.example`.

Итоговый блок (так должно быть, и так сейчас в репозитории):

```gitignore
# Secrets
.env
.env.*
!.env.example
```

Строка `!.env.example` с восклицательным знаком означает «а этот файл, наоборот, не игнорировать»: шаблон без значений нужно коммитить (раздел 6). Порядок важен: исключение должно идти **после** общего правила.

### 5.1 Урок: шаблон `.env.*` не совпадает с `.env`

При переносе правила в отдельный блок строка `.env` случайно пропала, и остались только `.env.*` и `!.env.example`. Шаблон `.env.*` требует **точку после `env`**, поэтому файлу с именем ровно `.env` он **не соответствует**. Результат: `.env` перестал игнорироваться, и `git add .` отправил бы секрет в коммит.

Что помогло найти проблему: проверка командой

```bash
git check-ignore -v .env
```

Пустой вывод (код возврата 1) означает «не игнорируется». На момент проверки в репозитории отслеживался только `.env.example`, так что утечки не было, и строку вернули (коммит `d9dfa2a`).

**Правило на будущее:** после *любой* правки `.gitignore` выполняй три проверки:

```bash
git check-ignore -v .env           # должна вывести строку с номером правила
git check-ignore -v .env.example   # должна быть пустой (он не игнорируется, так и надо)
git ls-files | grep -i '\.env'     # в списке только .env.example
```

Они занимают несколько секунд и ловят ровно такие ошибки.

## 6. Файлы .env и .env.example

### 6.1 Что это

- **`.env`**: реальные значения секретов. **Никогда не коммитится.** Лежит только на твоей машине.
- **`.env.example`**: шаблон с теми же именами, но **без значений**. Коммитится. Он показывает проверяющему и тебе самому будущему, какие переменные нужны.

Формат (имена соответствуют тому, как называются данные приложения в интре):

```text
UID=
SECRET=
```

### 6.2 Статус

- ✅ **`.env.example` создан** и закоммичен (коммит `e4772bd`). В первом коммите его не было, он добавлен позже. Значений в нём нет.
- ✅ **`.env` создан** на этапе регистрации приложения в интре. Он игнорируется git (раздел 5). Его рекомендуется закрыть от других пользователей машины командой `chmod 600 .env` (выполнение этой команды в ходе работы не подтверждалось).

**Ловушка с именем `UID`.** `UID` в zsh и bash это встроенная переменная только для чтения. Если загрузить `.env` командой `source .env`, присвоение упадёт с ошибкой вроде `read-only variable: UID`. Поэтому в [03](03-api-exploration.md) значения читаются через `grep` и `cut`. Если хочешь убрать ловушку совсем, переименуй переменные в `FT_UID` и `FT_SECRET` (в `.env` и `.env.example`). `flutter_dotenv` разбирает файл сам, так что ему имена безразличны.

### 6.3 Где лежит файл и что будет у проверяющего

Если код читает `.env`, то при чистой установке (клон репозитория без `.env`) приложение собрать или запустить без него не получится. Это нормально: секрет по определению в репозитории не лежит. На защите ты запускаешь **со своей машины, где `.env` есть**. Но о поведении при его отсутствии надо подумать: по крайней мере, приложение должно показать понятную ошибку, а не упасть.

## 7. Как секрет попадёт в приложение: отдельный риск

Это **не про git**, а про собранное приложение. Отдельный риск, о котором лучше сказать самим.

Планируемый способ читать `.env` во Flutter это пакет `flutter_dotenv`, и работает он так: `.env` подключается как **ассет** (прописывается в разделе `assets` файла `pubspec.yaml`). А ассеты упаковываются **внутрь APK**. APK это обычный zip-архив, поэтому секрет оттуда достаётся за пару минут: распаковал и прочитал.

Следствия:

- `.gitignore` защищает репозиторий, но **не защищает собранное приложение**.
- Любой, у кого есть твой APK, может достать из него `UID` и `SECRET`.
- Для учебного проекта это допустимо и это ожидаемая цена такого подхода, но **на защите об этом стоит сказать самим**, а не ждать вопроса.
- Если файл `.env` перечислен в ассетах, но на диске его нет, сборка Flutter, как правило, падает с ошибкой про отсутствующий ассет. Поэтому файл должен существовать локально, пусть и игнорируемый git.

Позже, когда ассеты будут настроены, это можно показать наглядно: собрать APK и посмотреть содержимое архива, например командой `unzip -l build/app/outputs/flutter-apk/app-debug.apk | grep -i env`.

### Альтернативы

| Подход | Как работает | Плюсы | Минусы |
|---|---|---|---|
| `flutter_dotenv` (планируем) | `.env` в ассетах, читается при запуске | Просто, понятно, соответствует заданию | Секрет в APK открытым текстом |
| `--dart-define-from-file` | Значения подставляются при сборке как константы, читаются через `String.fromEnvironment` | Нет отдельного файла в APK | Значения зашиты в бинарник, достать их сложнее, но можно; сборка требует лишнего флага |
| Ввод секрета в приложении при запуске | Пользователь вводит UID и SECRET сам | В APK секрета нет | Неудобно, противоречит идее «приложение само ходит в API» |
| Серверный посредник (бэкенд-прокси) | Секрет хранится на сервере, приложение ходит к нему | Это **правильный** способ для продакшена | Нужен свой сервер; за рамками задания |

Общий вывод: любой секрет, зашитый в мобильное приложение, в принципе извлекаем. По-настоящему безопасно только держать его на сервере.

## 8. Проверки перед каждым push

Привычка из нескольких команд, которая занимает полминуты:

```bash
git status                       # что изменилось и что в индексе
git diff --cached --stat         # сколько и каких файлов уйдёт в коммит
git ls-files | grep -i env       # какие env-файлы отслеживает git
git check-ignore -v .env         # правило игнорирования на месте?
```

Что должно быть в выводе:

- в `git status` и `git diff --cached --stat` **нет** `.env`, `.idea/`, `build/`, `local.properties`;
- `git ls-files | grep -i env` показывает **только `.env.example`** (или ничего, пока он не создан);
- `git check-ignore -v .env` выводит строку с номером правила.

**Поиск секрета в истории.** Реальный секрет мы ищем по первым 6–8 символам, а не по всему значению, чтобы он не оседал целиком в истории команд оболочки (`~/.zsh_history`):

```bash
git log --all -p -S'первые_символы' | head
```

Пустой вывод значит, что такой строки в истории нет. Не вставляй секрет целиком в команды, которые попадают в историю терминала.

## 9. Если секрет всё-таки утёк

Порядок действий (чем раньше, тем лучше):

1. **Сразу сделать старый секрет недействительным.** Если интра позволяет перегенерировать секрет приложения, перегенерируй его; если нет, удали приложение и зарегистрируй новое. Это самый важный шаг: после него то, что осталось в истории, уже не работает. (Какие именно кнопки есть в интре, я не проверяла.)
2. **Оценить, что в истории.** Команда из раздела 8 покажет, в каких коммитах секрет.
3. **Почистить историю.** Варианты:
   - **Пересоздать репозиторий.** Для маленького проекта самый простой и надёжный путь: создать новый репозиторий, перенести туда чистые файлы, а старый удалить.
   - **Переписать историю** специальными инструментами (например, `git filter-repo` или BFG Repo-Cleaner) и принудительно запушить. Это сложнее, и у других людей или на GitHub могут остаться копии старых объектов.
4. **Учесть требование задания.** Проверяющие смотрят историю: даже перегенерированный секрет, оставшийся в старых коммитах, может быть засчитан как нарушение. Поэтому историю нужно чистить, а не просто обновлять секрет.

Главный вывод: исправлять утечку мучительно, поэтому все проверки из раздела 8 нужно делать **до** push, а не после.

## 10. Альтернативы и инструменты

- **`gitleaks`, `git-secrets`, `detect-secrets`**: утилиты, которые ищут секреты в коммитах и могут срабатывать как pre-commit-хуки. Мы их не используем: для двух файлов и одного секрета достаточно ручной проверки. Но на больших проектах без них не обойтись.
- **GitHub secret scanning и push protection**: GitHub умеет предупреждать об известных форматах секретов. Распознаёт ли он формат секретов интры 42, я не проверяла, поэтому полагаться на него нельзя.
- **Хуки Git (`pre-commit`)**: можно автоматически запрещать коммит, если в индексе есть файл `.env`. Для этого проекта избыточно, но как идея полезно знать.

## 11. Гигиена IDE: папка .idea

Android Studio хранит настройки проекта в папке `.idea/`. Они индивидуальны для машины и в репозиторий не нужны. Flutter-овский `.gitignore` уже содержит правила `.idea/` и `*.iml`.

Но в нашей истории возникла особенность: в индексе оказался файл `.idea/.gitignore` (его, видимо, добавила сама IDE: она предлагает «Add to Git» при создании файлов). Игнорирование **не снимает** уже добавленный в индекс файл (раздел 3), поэтому его пришлось убирать командой `git rm --cached .idea/.gitignore`.

Чтобы IDE больше так не делала, можно отключить автодобавление в настройках: **Settings → Version Control → Confirmation**, раздел про добавление при создании файлов (точное название пункта зависит от версии IDE: ищи по смыслу «не добавлять автоматически»).
