# Swifty Companion

Учебный проект школы 42 Barcelona: мобильное приложение, которое по логину показывает профиль студента школы 42 (фото, уровень, навыки, проекты). Данные берутся из официального API интры.

| | |
|---|---|
| **Школа / ветка** | 42, Outer Core, ветка Mobile: *Mobile Initiation → Swifty Companion* |
| **Стек** | Flutter (Dart), HTTP-клиент, OAuth2 (client credentials) к API 42 |
| **Платформа** | Android; тестирование на реальном телефоне по USB (эмулятор на машинах кампуса не тянет) |
| **Язык документации** | Русский |

> **Как читать эту документацию.** Задание не требует README, поэтому он ведётся «по-нашему»: это конспект для обучения, а не визитка проекта. Поэтому он подробнее обычного: с теорией, рисками, подводными камнями и альтернативами.

## 4. Почему Flutter и Dart

### 4.1 Что такое Flutter

Flutter это open-source фреймворк Google для построения интерфейсов. Одна кодовая база даёт мобильные (Android, iOS), веб- и десктопные приложения. Язык фреймворка Dart. Лицензия BSD (новая BSD).

**Как он устроен (по-простому):**

- **Всё это виджет.** Интерфейс описывается деревом неизменяемых объектов-описаний (`Scaffold`, `Column`, `Text`, `ElevatedButton` и т. д.). Когда состояние меняется (`setState`), Flutter перестраивает затронутую часть дерева и перерисовывает только то, что изменилось.
- **Flutter рисует интерфейс сам.** Он не использует нативные кнопки и списки операционной системы, а отрисовывает каждый пиксель собственным движком (исторически на Skia, сейчас на Impeller). Поэтому интерфейс выглядит одинаково на разных платформах и версиях ОС.
- **Dart работает в двух режимах.** В debug-сборке Dart выполняется в виртуальной машине с JIT-компиляцией, поэтому возможен **hot reload**: изменённый код подгружается в уже работающее приложение за секунду, а состояние сохраняется. В release-сборке Dart компилируется заранее (AOT) в машинный код.

### 4.2 Какую проблему решает

Раньше под Android и iOS писали два отдельных приложения на разных языках (Kotlin/Java и Swift/Objective-C) двумя командами. Flutter позволяет написать один код на обе платформы и получить одинаковый вид. Для нас это ещё и возможность выучить новый стек: Android-ветка (ft_hangouts) уже пройдена, и повторять то же самое меньше смысла.

### 4.3 История (проверено по Википедии)

| Дата | Событие |

| 2015 | Проект показан под названием **Sky** на саммите разработчиков Dart |

Язык Dart тоже создан в Google (по моим сведениям, он анонсирован в 2011 году; эту дату я не перепроверяла).

### 4.4 Насколько он распространён в 2026

Если коротко: **Flutter один из двух главных кроссплатформенных фреймворков**, но с цифрами нужна осторожность.

- В опросе Stack Overflow 2025 Flutter использовали **9,12 %** респондентов, React Native **8,43 %** (в пересказе блога; доли считаются от всех респондентов, поэтому числа небольшие, а разрыв невелик).
- Часто цитируемые «46 % против 35 %» это данные Statista по опросу **2023 года** о долях среди разработчиков кроссплатформы. Подавать их как цифру 2026-го нельзя, хотя многие блоги так делают.
- Актуальная стабильная версия: Flutter 3.47.1 вышел 19 августа 2026 (по данным документации Shorebird). У нас установлена **3.47.7**. Следующая версия 3.50 запланирована на ноябрь 2026.
- Для рынка труда в Барселоне это нужно проверять отдельно (InfoJobs, LinkedIn): спрос на нативную Android/iOS-разработку и на React Native тоже заметный.

### 4.5 Альтернативы, которые мы рассматривали

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| **Kotlin + Jetpack Compose** | Нативный Android, меньше рисков, мощная экосистема Android | Только Android. Compose после «чистого» Android SDK это новая парадигма, так что учиться всё равно пришлось бы | Меньше нового: Android уже пройден в ft_hangouts |
| **Java + XML-разметка** | Самый безопасный и знакомый путь | Устаревающий подход, на защите будет вопрос «зачем», а ответ «потому что знаю» слабый | Не даёт нового навыка |
| **React Native** (JavaScript/TypeScript) | Огромная экосистема, нативные компоненты, много вакансий | Нужен Node-стек и JS-экосистема; в задании прямо упомянут Flutter, а не RN | Менее очевидный выбор в рамках задания |
| **Нативный Swift (iOS)** | Родной язык iOS | Для сборки под iOS нужны macOS и Xcode, а машины кампуса работают на Linux | Технически недоступен |
| **Kotlin Multiplatform / Compose Multiplatform** | Общий код между платформами на Kotlin | Более молодая и менее знакомая связка | Лишний риск для первого проекта на фреймворке |

### 4.6 Минусы Flutter и риски (о них лучше сказать самим)

- **Размер приложения.** Flutter упаковывает свой движок, поэтому приложение тяжелее нативного.
- **Платформенные возможности идут через плагины.** Если нужной функции нет, придётся писать нативный код на Kotlin/Swift.
- **Свой набор виджетов.** Интерфейс не «родной», а имитирует его, поэтому после обновления ОС возможны небольшие расхождения.
- **Скорость изменений.** Flutter выходит новыми версиями несколько раз в год. Например, в 3.47 виджеты Material и Cupertino вынесли в отдельные пакеты (по документации Shorebird). Туториалы двухлетней давности могут устареть.
- **Зависимость от Google.** Код открыт (BSD) и его можно форкнуть, но развитием управляет Google. Подтверждённый пример: 29 октября 2024 года появился форк **Flock**, анонсированный из-за недовольства тем, сколько ресурсов Google вкладывает во Flutter (по статье LWN). Второй пример из памяти, не перепроверенный: Dart задумывался как замена JavaScript в Chrome, от этой идеи отказались, и язык ожил только благодаря Flutter.

Вывод для обоснования на защите: Flutter выбран, потому что (1) он упомянут в задании, (2) один код покрывает несколько платформ, (3) он даёт новый навык после уже пройденной Android-ветки, (4) hot reload сильно ускоряет работу на слабых машинах, (5) для задачи «два экрана и HTTP» его возможностей с запасом хватает. Минусы мы знаем и назвали выше.

## 5. Как будет работать 42 API (план)

> ✅ Раздел сверен с **реальным ответом API** (замер 17 октября 2026). Теория, скрипты с построчным разбором и все находки: [docs/03-api-exploration.md](docs/03-api-exploration.md). Открытые вопросы (в первую очередь формула процента скилла) перечислены там же.

Для нашей задачи нужен **OAuth2, Client Credentials flow**: приложение авторизуется от своего имени, без входа пользователя.

1. В интре регистрируем новое приложение (в моём плане был путь Settings → API → Register a new app, в официальном гайде путь меню не указан). Получаем **UID** и **SECRET** и кладём в `.env`.
2. Запрашиваем токен: `POST https://api.intra.42.fr/oauth/token` с параметрами `grant_type=client_credentials`, `client_id`, `client_secret`. В ответе приходят `access_token` и срок жизни `expires_in` (в официальном гайде пример токена живёт 7200 секунд, то есть два часа).
3. Запрашиваем профиль: `GET https://api.intra.42.fr/v2/users/{login}` с заголовком `Authorization: Bearer <token>`.

Токен client credentials не привязан к студенту и даёт **только публичные данные**.

Карта полей (проверена на реальном ответе):

| Что нужно | Где в ответе |
|---|---|
| Поля профиля | `login`, `displayname`, `email`, `phone`, `location`, `wallet`, `correction_point` (в единственном числе), `pool_month`, `pool_year` |
| Фото | `image.versions` (`large`, `medium`, `small`, `micro`) и `image.link` |
| Уровень | `cursus_users[]` → `level` (дробное число). Основной курс определяем по `cursus.slug == "42cursus"`: у студента может быть несколько курсов |
| Скиллы | `cursus_users[]` → `skills[]`: только `id`, `level`, `name`. **Процента в API нет**, считаем сами: `level / 20 × 100` (максимум 20 косвенно подтверждён масштабом радара в интре, см. docs/03, раздел 11) |
| Проекты | `projects_users[]` → `status` (`finished` значит завершён), `validated?` (`true`, `false` или `null`), `final_mark`, `project.name` |
| Скрытые данные | Скрытое приходит строкой `"hidden"` (например, `phone`), а не `null`. Показываем «N/A» |

Важные нюансы (подробности в docs/03): уровни приходят с шумом чисел с плавающей точкой (`3.4699999999999998`), поэтому при показе округляем; любое поле может быть пустым, поэтому разбор JSON должен быть устойчивым; «Expertises» (звёзды «мне интересно») это не «Skills» из задания.

Пошаговая симуляция работы с токеном:

```text
Запуск: токена в памяти нет
Ввод логина → проверка (trim, не пусто)
  → получить токен: кэш пуст → POST /oauth/token → запоминаем токен и время истечения
  → GET /v2/users/<login> → 200 → разбор → переход на экран профиля
Назад, второй поиск другого логина
  → получить токен: кэш жив → POST НЕ делаем
  → GET → 404 → сообщение «логин не найден» на первом экране
...время жизни токена истекло
  → получить токен: срок вышел → новый POST → дальше как обычно (бонус)
```

## 6. Архитектура (план)

Это набросок, он будет уточняться по мере работы.

```text
lib/
  main.dart            точка входа
  core/                токен-сервис, HTTP-клиент, типы ошибок
  models/              пользователь, скилл, проект
  data/                репозиторий: «получить пользователя по логину»
  ui/                  экран поиска, экран профиля
```

- **Состояние:** для двух экранов достаточно `setState` и `FutureBuilder`. Provider, Riverpod и Bloc здесь были бы избыточны, а на защите вопрос «зачем» окажется сложнее ответа.
- **Планируемые зависимости:** `http` (запросы) и `flutter_dotenv` (чтение `.env`). Альтернатива `dio` удобнее (перехватчики для ошибки 401), но это лишняя зависимость. Каждую зависимость придётся обосновывать на защите.
- **Токен:** один экземпляр сервиса хранит токен и время истечения, обновляет токен при необходимости и защищён от параллельных запросов токена.

## 8. Быстрый старт

Подробно и с объяснениями: [docs/01-environment.md](docs/01-environment.md). Кратко, при настроенном окружении:

git clone git@github.com:Knowledge82/swifty-companion.git

flutter pub get
flutter devices                  # убедиться, что телефон виден

## 10. Безопасность и секреты

Требование задания жёсткое: учётные данные только в `.env`, который не попадает в git. Если секрет хотя бы раз попал в коммит, **он остаётся в истории даже после удаления файла**.

Что уже сделано: правило `.env` стоит в `.gitignore` и проверено командой `git check-ignore -v .env`. По дороге мы поймали и исправили ошибку, при которой строка `.env` случайно пропала из `.gitignore` (подробности и правило проверки после любой правки: [docs/02-git-and-secrets.md](docs/02-git-and-secrets.md), раздел 5).
