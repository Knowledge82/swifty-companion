## 1. Картина целиком

```
.env ──(сборка)──▶ ассет внутри APK
                       │
main() ── dotenv.load ─▶ AppConfig.fromMap ──сбой──▶ ConfigErrorApp (экран ошибки)
   │ ок
   ▼
_buildDependencies:  TokenService ─┬▶ ApiClient ──▶ UserRepository
   (один на всё приложение)        └▶ PhotoLoader
   ▼
SwiftyApp (MaterialApp: тема, переводы es/en) ─▶ SplashScreen ─▶ SearchScreen
                                                                    │ «Поиск»
              validateLogin ─(плохой логин)─▶ ошибка под полем, сети нет
                    │ ок
                    ▼
      UserRepository.fetchUser ─▶ ApiClient.getJson ─▶ TokenService.getToken
                                          │                    │ (нет живого токена)
                                          │                    └▶ POST /oauth/token
                                          ▼
                       GET /v2/users/<login> + Bearer <токен>
                                          ▼
                       UserProfile.fromJson ─▶ ProfileScreen
                                                    └▶ ProfileAvatar ─▶ PhotoLoader.load
```

Одной фразой: приложение по `UID` и `SECRET` получает у API 42 временный токен, с ним запрашивает JSON профиля, безопасно разбирает его в модель и рисует экран; любой сбой по дороге превращается в понятное сообщение.

## 2. Пошаговый флоу

### Шаг 0. Сборка: куда попадает секрет

- **Что.** Файл `.env` с `FT_UID` и `FT_SECRET` объявлен в `pubspec.yaml` как ассет и при сборке упаковывается внутрь APK. В git его нет, `.gitignore` его закрывает.
- **Где.** `pubspec.yaml` (раздел `assets`), `.gitignore`, `android/app/build.gradle.kts` (блок `androidResources`, чтобы файл с точкой в имени не пропадал при упаковке).
- **Зачем.** Требование задания: секреты хранятся только в `.env`, который не попадает в git.
- **Цена.** Секрет лежит в APK открытым текстом, APK это zip. Этот компромисс описан честно и обсуждается на защите.
- **Ловушка.** Ассет, объявленный в `pubspec.yaml`, ещё не гарантирует, что файл попал в APK. Проверка: `unzip -l app.apk | grep -i env`.
- **Подробнее.** [02, раздел 6](02-git-and-secrets.md#6-файлы-env-и-envexample) и [раздел 7](02-git-and-secrets.md#7-как-секрет-попадёт-в-приложение-отдельный-риск); [05, раздел 3](05-config-and-skeleton.md#3-как-env-попадает-в-приложение) и [инцидент 3.1](05-config-and-skeleton.md#31-инцидент-env-объявлен-сборка-прошла-а-в-apk-файла-нет); [14, раздел 8.2](14-remaining-work.md#82-ограничение-о-котором-надо-сказать-самим).

### Шаг 1. Старт: `main()`

- **Что.** `WidgetsFlutterBinding.ensureInitialized()`, потом всё внутри `try`. Первым делом `dotenv.load(fileName: '.env')` достаёт ассет из APK.
- **Где.** `lib/main.dart`.
- **Зачем.** `ensureInitialized` нужен потому, что до `runApp` мы уже обращаемся к платформе (читаем ассет). Без него вызов упадёт.
- **Подробнее.** [16, раздел 2](16-code-walkthrough.md#2-точка-входа-и-запуск-по-шагам); про `async` и `await` [04, раздел 5](04-dart-flutter-basics.md#5-асинхронность-future-async-await).

### Шаг 2. Конфиг: `AppConfig.fromMap`

- **Что.** Словарь из `dotenv.env` превращается в объект `AppConfig`: значения обрезаются по краям, оба ключа (`FT_UID`, `FT_SECRET`) должны быть непустыми. Иначе `ConfigException` со списком недостающих.
- **Где.** `lib/core/config.dart`.
- **Зачем.** Один раз при старте превращаем «словарь строк» в типизированный объект. Код дальше не обращается к `dotenv` напрямую, а тесты проверяют `AppConfig` без Flutter и без настоящего `.env`. `toString()` переопределён и показывает `***`, чтобы `print(config)` не вывел секрет.
- **Подробнее.** [05, раздел 2](05-config-and-skeleton.md#2-почему-appconfigfrommap-а-не-прямое-чтение-dotenv); [16, раздел 8](16-code-walkthrough.md#8-configdart-api_constantsdart-api_exceptiondart).

### Шаг 3. Сбой конфига: запасное приложение

- **Что.** Две ветки `catch`. Узкая (`on ConfigException`) показывает, каких ключей не хватает. Широкая (`catch (error, stackTrace)`) ловит всё остальное и показывает «файл нечитаем». В debug она печатает тип ошибки и стек, но не текст сообщения, потому что в нём может оказаться что угодно, в том числе секрет. Обе ветки запускают `ConfigErrorApp` и на этом программа заканчивается.
- **Где.** `lib/main.dart` (оба `catch`), `lib/ui/config_error_screen.dart`.
- **Зачем.** Вместо белого экрана пользователь видит причину. `ConfigErrorApp` это отдельный `MaterialApp` со своей темой и переводами, потому что до сбоя основного приложения ещё нет. Внутри `Builder`, чтобы `AppStrings.of(context)` искал переводы **ниже** `MaterialApp`, а не выше.
- **Ловушка.** После правки `.env` нужна полная пересборка (`R` не хватит), потому что файл лежит в ассетах.
- **Подробнее.** [05, раздел 7](05-config-and-skeleton.md#7-что-может-пойти-не-так) и [раздел 1](05-config-and-skeleton.md#1-файлы-и-что-в-них).

### Шаг 4. Сборка зависимостей

- **Что.** Создаётся **один** `TokenService`. Поверх него `ApiClient` (запросы профиля) и `PhotoLoader` (фото), оба берут токен у общего сервиса. Сверху `UserRepository`, обёртка над `ApiClient`. Журнал подключается только в debug (`kDebugMode`).
- **Где.** `lib/main.dart`, функция `_buildDependencies`.
- **Зачем.** Токен общий для всего приложения и запрашивается один раз. Зависимости передаются в конструкторы (внедрение зависимостей), поэтому тесты подставляют поддельные.
- **Подробнее.** [09, раздел 2](09-first-live-run.md#2-граф-зависимостей-di) и [раздел 7](09-first-live-run.md#7-журнал-для-отладки).

### Шаг 5. Интерфейс: `SwiftyApp`

- **Что.** `MaterialApp` с темой steampunk и переводами (испанский по умолчанию, английский по языку телефона). `home`: если `introEnabled`, то `SplashScreen`, который после показа переходит к `SearchScreen`, иначе сразу поиск. Экран поиска создаётся один раз как локальная переменная в `build`.
- **Где.** `lib/main.dart` (`SwiftyApp`), `lib/l10n/` (`AppStrings` и два языка), `lib/ui/steampunk/steampunk_theme.dart`, `lib/ui/splash_screen.dart` (переключатель `introEnabled`).
- **Зачем.** Требования задания про оформление и язык. Переводы устроены так, что любой язык, кроме английского, получает испанский.
- **Ловушка.** Локальная переменная, а не поле класса: инициализатор поля не может использовать другие поля, а класс с `const`-конструктором допускает только `final`-поля, которые являются константами или параметрами конструктора.
- **Подробнее.** [10, разделы 2–4](10-localization-and-photo.md#2-локализация-теория); [12, раздел 6](12-steampunk-design.md#6-тема-приложения); [13, раздел 3](13-icon-and-splash.md#3-теория-экран-запуска) и [раздел 9](13-icon-and-splash.md#9-фото-на-экране-заставке).

### Шаг 6. Экран поиска: ввод и проверка

- **Что.** Пользователь вводит логин и нажимает «Поиск». Сначала защита от двойного нажатия: `if (_loading) return;` первой строкой `_submit()`, флаг `_loading` ставится синхронно до первого `await`. Потом `validateLogin`: только `a-z`, `0-9`, `-`, `_`, не пусто. Не прошло — ошибка под полем, **сети нет**.
- **Где.** `lib/ui/search_screen.dart`, `lib/core/login.dart`.
- **Зачем.** Мусор не уходит на сервер, лимит запросов не тратится, а ещё это защита от подстановки в адрес запроса. Флаг сбрасывается на каждом выходе (успех, `ApiException`, общий `catch`), и после каждого `await` стоит `if (!mounted) return`.
- **Подробнее.** [05, раздел 4](05-config-and-skeleton.md#4-валидация-логина); [09, раздел 3](09-first-live-run.md#3-состояния-экрана-поиска) и [раздел 5](09-first-live-run.md#5-ловушки-async-во-flutter).

### Шаг 7. Репозиторий

- **Что.** `fetchUser` ещё раз проверяет логин (не доверяет интерфейсу), нормализует (обрезать, нижний регистр) и просит у `ApiClient` путь из сегментов `['v2', 'users', login]`. Ответ превращается в `UserProfile`; `FormatException` превращается в «неожиданный ответ».
- **Где.** `lib/data/user_repository.dart`.
- **Зачем.** Слои не знают друг о друге лишнего: интерфейс не знает про HTTP, клиент не знает про модель. Сегменты пути кодируются сами, строку адреса руками мы не склеиваем.
- **Подробнее.** [08, раздел 9](08-api-client.md#9-репозиторий) и [раздел 2](08-api-client.md#2-теория-слои-и-зачем-они).

### Шаг 8. Токен: из памяти или из сети

- **Что.** `getToken()`: в памяти есть живой токен (срок минус запас 60 с) — сразу его. Нет — один запрос `POST /oauth/token` с `grant_type=client_credentials`, секрет в теле формы, не в адресе. Если токен просят сразу несколько мест, запрос один: `_pending` хранит текущий `Future`, остальные присоединяются. Ответ 200: запоминаем токен и `expires_in` (нет поля — час по умолчанию).
- **Где.** `lib/core/token_service.dart`.
- **Зачем.** OAuth2 в варианте Client Credentials: приложение авторизуется само, без участия пользователя, поэтому видны только публичные данные. Не плодим запросы за токеном (требование задания), секрет не попадает ни в журнал, ни в адрес.
- **Статусы.** 400/401/403 — `AuthException`, 429 — `RateLimitException`, 5xx — `ServerException`, остальное — `UnexpectedResponseException`.
- **Бонус задания (токен пересоздаётся сам).** Два механизма. Упреждающий: за 60 секунд до конца срока токен считается просроченным. Реактивный: см. шаг 9, повтор после 401.
- **Подробнее.** [07, разделы 2–6](07-token-service.md#2-теория-что-такое-токен-и-почему-он-временный); [03, раздел 2](03-api-exploration.md#2-теория-oauth2-и-client-credentials); как показать бонус [14, раздел 6](14-remaining-work.md#6-бонус-как-показать-что-токен-пересоздаётся).

### Шаг 9. Запрос профиля

- **Что.** `GET https://api.intra.42.fr/v2/users/<login>` с `Authorization: Bearer <токен>`. Ответ 401: токен выбрасывается (`invalidate` с тем самым токеном, с которым ушёл запрос), берётся новый, запрос повторяется **ровно один раз**. 404 — `NotFoundException`. Любой запрос обёрнут таймаутом 15 секунд, сетевые сбои превращаются в типизированные исключения.
- **Где.** `lib/core/api_client.dart`, `lib/core/http_helpers.dart`, `lib/core/api_exception.dart`.
- **Зачем.** Токен мог быть отозван раньше срока. Повтор один, чтобы не было бесконечного цикла. Тело ответа читается из **байтов** как UTF-8, а не из `response.body`: иначе при отсутствии кодировки в заголовке кириллица и диакритика портятся.
- **Подробнее.** [08, разделы 3–7](08-api-client.md#3-запрос-адрес-метод-заголовки); [07, раздел 7](07-token-service.md#7-ошибки-закрытое-семейство-apiexception).

### Шаг 10. Разбор ответа в модель

- **Что.** `UserProfile.fromJson` читает поля безопасными читалками: нет поля или оно не того типа — `null`, а не падение. Нет `login` — `FormatException`. Из JSON собираются курсы с уровнем, скиллы (процент равен уровню, делённому на 20), завершённые проекты.
- **Где.** `lib/core/json_reader.dart`, `lib/models/user_profile.dart`, `lib/models/cursus_progress.dart`, `lib/models/skill.dart`, `lib/models/project_result.dart`.
- **Зачем.** API неровное: разные поля скрыты или пусты у разных студентов. Лучше показать частичные данные, чем упасть.
- **Подробнее.** [06, разделы 2–5](06-models.md#2-теория-что-такое-разбор-json-и-где-он-ломается); [16, раздел 4](16-code-walkthrough.md#4-json_readerdart-чтение-json-без-падений); находки по реальному ответу [03, раздел 8](03-api-exploration.md#8-находки-по-реальному-ответу).

### Шаг 11. Раскладка проектов по разделам

- **Что.** `finishedProjectsBySection()` берёт завершённые проекты (новые сверху) и для каждого вызывает `sectionOf`: **сначала по курсу, потом по slug**. Курс решает для писин и посторонних курсов (Discovery Piscine и подобные дают отдельный раздел с названием курса из API). Если курс не решил, `categoryOf` смотрит на slug: `c-piscine`/`piscine` — Piscina, список `commonCoreSlugs` и шаблоны `cpp-module-NN`, `exam-rank-NN`, `python-module-NN` — Common Core, всё остальное — Outer Core. Проект из `42cursus` никогда не попадает в Piscina по slug.
- **Где.** `lib/models/user_profile.dart`, `lib/models/project_section.dart`, `lib/models/project_category.dart`.
- **Зачем.** Common Core и Outer Core живут в одном курсе `42cursus`, различить их можно только по списку slug. Неизвестный новый проект по умолчанию попадает в Outer Core и не теряется. `ProjectSection` это `sealed class`: компилятор заставляет интерфейс обработать оба вида разделов.
- **Подробнее.** [12, раздел 9](12-steampunk-design.md#9-проекты-по-разделам), [раздел 21](12-steampunk-design.md#21-итерация-8-новая-программа-common-core) и [раздел 24](12-steampunk-design.md#24-итерация-11-разделы-проектов-по-курсу-а-не-только-по-slug); [11, раздел 3](11-profile-content.md#3-проекты-что-считается-завершённым).

### Шаг 12. Переход на профиль

- **Что.** Если пользователь успел уйти с экрана, `if (!mounted) return` не даёт навигировать «в никуда». Иначе `Navigator.push(ProfileScreen(profile, loadPhoto: photoLoader.load))`, индикатор до этого сбрасывается.
- **Где.** `lib/ui/search_screen.dart`.
- **Подробнее.** [04, раздел 9](04-dart-flutter-basics.md#9-навигация-стек-экранов).

### Шаг 13. Экран профиля

- **Что.** Шапка с именем и логином, аватар, полоса уровня, статус (лампочка «в кампусе / нет»), контакты, скиллы с процентами, проекты по разделам. Поля, которых API не дал, не показываются. Для отдельных логинов под именем пасхалка (переключатель `easterEggsEnabled`).
- **Где.** `lib/ui/profile_screen.dart`, `lib/ui/skills_section.dart`, `lib/ui/projects_section.dart`, `lib/ui/easter_egg.dart`, оформление в `lib/ui/steampunk/`.
- **Зачем.** Адаптивность через ограничения (`ConstrainedBox`, `Wrap`, прокрутка), чтобы ничего не вылезало при повороте и крупном шрифте.
- **Подробнее.** [11, разделы 1–5](11-profile-content.md#1-что-на-экране); [12](12-steampunk-design.md) целиком; [14, раздел 4](14-remaining-work.md#4-адаптивность).

### Шаг 14. Фото

- **Что.** Из JSON берутся до двух `https`-адресов. `ProfileAvatar` перебирает их по очереди, любая ошибка означает «пробуем следующий», в конце заглушка. `PhotoLoader.load` проверяет адрес (только `https`, хост из белого списка `photoHosts`, порт 443), смотрит в кэш (до 20 картинок, выселяется самая старая по времени добавления, это FIFO, а не LRU), качает с тем же токеном, лимит 5 МБ.
- **Где.** `lib/models/user_profile.dart` (`_pickImageUrls`), `lib/ui/profile_avatar.dart`, `lib/data/photo_loader.dart`, `lib/core/api_constants.dart` (`photoHosts`).
- **Зачем.** CDN отдаёт фото только с токеном, поэтому обычный `Image.network` не годится. Адрес приходит с сервера, и подделанный чужой адрес получил бы наш токен, отсюда белый список. Фото не критично: при 401/403 токен заново не запрашивается.
- **Подробнее.** [10, раздел 1](10-localization-and-photo.md#1-фото-история-причина-и-решение).

## 3. Путь ошибки

Любая ошибка по дороге проходит один и тот же путь.

1. Источник бросает типизированное исключение. Все ошибки API наследуют от `sealed class ApiException`: `NetworkException`, `AuthException`, `NotFoundException`, `RateLimitException`, `ServerException`, `UnexpectedResponseException`. Файл `lib/core/api_exception.dart`.
2. Экран поиска ловит `ApiException`, сбрасывает индикатор и показывает `ErrorBanner` с текстом на языке телефона (`lib/ui/error_banner.dart`, строки в `lib/l10n/`). Кнопка снова активна.
3. Всё непредвиденное попадает в общий `catch`, превращается в «неожиданный ответ», стек пишется в журнал только в debug.
4. Ошибки конфига при старте идут отдельной дорогой (шаг 3) и показываются на отдельном экране.

Подробнее: [07, раздел 7](07-token-service.md#7-ошибки-закрытое-семейство-apiexception), [09, раздел 6](09-first-live-run.md#6-баннер-ошибок-и-исчерпывающий-switch), сценарии для телефона [14, раздел 3](14-remaining-work.md#3-сценарии-ошибок-на-телефоне).

## 4. Сквозные принципы

1. **Проверять рано, до сети.** Логин, адрес фото, конфиг.
2. **Секреты не светятся.** Ни в журнале, ни в адресе запроса, ни в `toString()`; ошибка при старте логирует тип и стек, но не текст.
3. **Любой сбой превращается в сообщение.** Типизированные исключения вместо «что-то пошло не так».
4. **Недоверие к данным API.** Любое поле может быть `null`, любой адрес картинки может быть подделан.
5. **Слои не знают друг о друге лишнего.** Интерфейс, репозиторий, клиент, токен-сервис; любой слой проверяется тестом отдельно.
6. **Журнал только в debug.** В release приложение молчит (`kDebugMode`).

## 7. Альтернативы архитектуры и риски

**Альтернативы.**

- *Authorization Code вместо Client Credentials.* Пользователь входит через интру и разрешает доступ. Нужно для личных данных человека; для просмотра публичных профилей избыточно, плюс потребовало бы экран входа и адрес возврата.
- *Сервер-посредник, который хранит секрет.* Правильное решение для настоящего продукта (секрет не едет в APK), но задание требует приложение без бэкенда.
- *`--dart-define-from-file` вместо `flutter_dotenv`.* Секрет не лежит в ассетах, но нужен флаг при каждом запуске и сборке; проверяющий без флага увидит ошибку.
- *Менеджер состояния (Provider, Riverpod, Bloc).* Для двух экранов и одной загрузки хватает `StatefulWidget` и `setState`; внешние пакеты добавили бы зависимость без выигрыша.
- *`dio` вместо `http`.* Удобные перехватчики, но больше зависимостей; наш повтор после 401 пишется в двадцать строк.
- *Готовый `Image.network` для фото.* Не добавляет токен, поэтому для CDN 42 не подходит.

**Риски.**

- Секрет в APK достаётся архиватором. Снижение: перегенерировать секрет после показа или завести демо-приложение в интре ([14, раздел 8.2](14-remaining-work.md#82-ограничение-о-котором-надо-сказать-самим)).
- Список `commonCoreSlugs` составлен по программе и по выгрузкам и может разойтись с реальными slug; он лежит в одной константе, чтобы править в одном месте.
- Поля API неровные и меняются; поэтому все поля необязательные.
- Новая версия Flutter у проверяющего может поднять минимумы инструментов или убрать устаревшее ([01, раздел 4.5](01-environment.md#45-версия-flutter-у-каждой-машины-своя), [17](17-material-ui-migration.md)).
- Лимит API около 2 запросов в секунду и 1200 в час: не спамить при демонстрации.
