## 1. Dart: переменные и типы

Dart статически типизирован (как C++), но тип можно не писать, если он очевиден из значения.

```dart
int count = 3;            // целое
double level = 12.44;     // дробное
String login = 'vdarsuye';
bool ok = true;

var name = 'abc';         // тип выведен: String (потом сменить на число нельзя)
final id = 42;            // присвоить можно один раз, значение известно в рантайме
const pi = 3.14;          // константа времени компиляции
```

Разница `final` и `const`:

| | Когда значение известно | Пример |
|---|---|---|
| `final` | при выполнении программы | `final now = DateTime.now();` |
| `const` | уже при компиляции | `const EdgeInsets.all(24)` |

В Flutter `const` перед виджетом означает «этот виджет никогда не меняется, не пересоздавай его». Это оптимизация, а линтер (`flutter_lints`) подсказывает, где её можно поставить.

Интерполяция строк: `'Привет, $login'` или `'${a + b}'` для выражений.

## 2. Null safety: самое важное для разбора JSON

В Dart обычный тип **не может быть `null`**. Если значение может отсутствовать, к типу добавляют `?`.

```dart
String a = 'x';     // null присвоить нельзя, компилятор не даст
String? b;          // может быть строкой или null
```

Операторы, которыми мы будем пользоваться постоянно:

| Оператор | Что делает | Пример |
|---|---|---|
| `?.` | вызывает, только если не `null`; иначе даёт `null` | `b?.length` |
| `??` | значение по умолчанию, если слева `null` | `b ?? 'N/A'` |
| `!` | «клянусь, тут не `null`» (если соврал, падение) | `b!.length` |
| `??=` | присвоить, если сейчас `null` | `b ??= 'x'` |

**Почему это критично именно для нашего проекта.** JSON от API 42 полон «дыр»: у проекта может не быть `final_mark`, у пользователя `phone` приходит строкой `"hidden"`, а не `null` ([docs/03](03-api-exploration.md)). Если описать поле как `String`, а придёт `null`, приложение упадёт на разборе. Поэтому поля, которые API может не дать, мы объявляем как `String?`/`int?`, а при показе подставляем `N/A`.

Из реального кода, [`lib/core/config.dart`](../lib/core/config.dart):

```dart
final id = env['FT_UID']?.trim() ?? '';
```

Читается слева направо:
1. `env['FT_UID']` достаёт значение из словаря. Тип результата `String?`, потому что ключа может не быть.
2. `?.trim()` убирает пробелы по краям, **если** значение не `null`. Если `null`, всё выражение пока `null`.
3. `?? ''` если получилось `null`, берём пустую строку.

Симуляция на трёх входах:

| `env['FT_UID']` | после `?.trim()` | после `?? ''` |
|---|---|---|
| `' abc '` | `'abc'` | `'abc'` |
| `'   '` | `''` | `''` |
| ключа нет (`null`) | `null` | `''` |

Во всех случаях дальше работаем с обычной `String`, проверка `id.isEmpty` ловит и «нет ключа», и «пусто», и «одни пробелы».

## 3. Классы, конструкторы, `factory`

```dart
class AppConfig {
  const AppConfig({required this.clientId, required this.clientSecret});

  final String clientId;
  final String clientSecret;
}
```

Построчно:
- `const AppConfig(...)` конструктор. Запись `this.clientId` сразу кладёт аргумент в поле (аналог списка инициализации в C++).
- Фигурные скобки `{...}` делают параметры **именованными**: вызов `AppConfig(clientId: 'a', clientSecret: 'b')`.
- `required` значит «обязателен». Без него именованный параметр должен быть nullable или иметь значение по умолчанию.
- `final` поля неизменяемы после создания. Для моделей данных это правило хорошего тона.

**`factory`-конструктор** это конструктор, который может содержать логику и вернуть уже существующий объект или бросить исключение. В Dart по нему принято делать разбор: `AppConfig.fromMap(...)`, позже `UserProfile.fromJson(...)`.

```dart
factory AppConfig.fromMap(Map<String, String> env) {
  ...
  return AppConfig(clientId: id, clientSecret: secret);
}
```

Всё, что нужно для проверки данных (пусто, нет поля), лежит в одном месте, и это место легко тестировать.

## 4. Коллекции и «collection if»

```dart
final list = <int>[1, 2, 3];                  // List<int>
final map  = <String, int>{'a': 1, 'b': 2};   // Map<String, int>
```

В API 42 JSON после разбора превращается в `Map<String, dynamic>` (ключи строки, значения «что угодно») и `List<dynamic>`. `dynamic` значит «тип проверяется только при выполнении», поэтому при разборе значения приводят к нужным типам явно (`as String?`, `as num?`).

**Collection if** это условие прямо внутри литерала списка:

```dart
final missing = <String>[
  if (id.isEmpty) 'FT_UID',
  if (secret.isEmpty) 'FT_SECRET',
];
```

Симуляция: `id` пуст, `secret` заполнен.
1. Создаётся пустой список.
2. `id.isEmpty` истинно, значит добавляется `'FT_UID'`.
3. `secret.isEmpty` ложно, не добавляется.
4. Итог: `['FT_UID']`, `missing.join(', ')` даст `FT_UID`.

Если пусты оба, получится `FT_UID, FT_SECRET`. Альтернатива: создать пустой список и по очереди `add` с `if` снаружи. Работает так же, но длиннее.

## 5. Асинхронность: `Future`, `async`, `await`

Сетевой запрос не может блокировать интерфейс, поэтому он выполняется «в фоне». Результат, которого ещё нет, представлен объектом **`Future<T>`** («будущее значение типа T»).

```dart
Future<void> main() async {
  await dotenv.load(fileName: '.env');   // ждём, не блокируя интерфейс
  ...
}
```

- `async` перед телом функции разрешает в ней `await`.
- `await` приостанавливает **эту функцию** до готовности `Future`, при этом всё остальное приложение продолжает работать (в отличие от `sleep()` в C).
- Функция с `async` сама возвращает `Future`.

Dart выполняет код в **одном потоке** (изолят) и управляется очередью событий. Поэтому `await` не создаёт параллельных потоков: пока ждёт сеть, поток свободен для отрисовки. Это упрощает жизнь (нет гонок за память), но важно для токен-сервиса на этапе 3: два `await` в разных местах могут «перемешаться» по времени, и два запроса токена могут уйти одновременно. Там мы это учтём.

Симуляция `main` в нашем проекте:

| Шаг | Что происходит |
|---|---|
| 1 | `WidgetsFlutterBinding.ensureInitialized()` готовит связь с платформой |
| 2 | `await dotenv.load(...)`: читается ассет `.env`, функция «спит» |
| 3 | Файл прочитан, `dotenv.env` заполнен, выполнение идёт дальше |
| 4 | `AppConfig.fromMap(...)` проверяет значения |
| 5 | `runApp(...)` показывает интерфейс |

## 6. Исключения

```dart
try {
  ...
} on ConfigException catch (e) {   // конкретный тип
  ...
} catch (_) {                      // любой другой
  ...
}
```

- `on Тип` ловит только указанный тип. `catch (e)` ловит всё.
- `_` вместо имени значит «значение мне не нужно».
- Порядок важен: более конкретные блоки идут первыми.
- `throw ConfigException(...)` бросает исключение. Любой объект можно бросить, но принято бросать наследников `Exception`.

На этапе 4 мы заведём `sealed class` для ошибок API (`NotFound`, `Unauthorized`, `NoNetwork` и так далее). Dart тогда проверит исчерпывающий `switch`, и забыть случай не получится. Подробнее будет в документе этапа 4.

## 7. Flutter: всё есть виджет

Этот раздел и два следующих самые важные во всём документе. Если их понять, остальной Flutter превращается в «то же самое, только больше». Поэтому идём медленно и с аналогиями.

### 7.1. Одна картинка в голове: интерфейс как матрёшка из функций

В C ты привык, что программа это последовательность команд: «нарисуй окно, потом нарисуй в нём кнопку, потом поменяй цвет кнопки». Во Flutter всё наоборот. Ты **описываешь результат целиком**: «вот экран, на нём колонка, в колонке поле и кнопка». А как именно это нарисовать и что поменять, когда данные изменились, решает Flutter.

Представь заказ в пиццерии. Есть два способа:

- **Императивно (как в C):** «возьми тесто, раскатай, положи соус, добавь сыр, поставь в печь на 8 минут». Ты командуешь каждым шагом.
- **Декларативно (как во Flutter):** «хочу пиццу пепперони, большую, без лука». Ты описываешь результат, повар разбирается сам.

Если передумал («без лука» превратилось в «с луком»), ты не говоришь повару «вынь лук обратно». Ты делаешь **новый заказ целиком**, а повар сам решает, что именно переделать. Именно так работает Flutter: данные поменялись, ты возвращаешь новое описание экрана, он сравнивает со старым и перерисовывает только отличия.

> **Виджет** это один «пункт в заказе»: описание того, что должно быть на экране. Кнопка это виджет. Текст это виджет. Отступ вокруг кнопки это тоже виджет (да, даже пустой отступ). Целый экран это виджет. Всё приложение это виджет.

### 7.2. Самый маленький пример, разбор по символам

```dart
Center(
  child: Text('Привет'),
)
```

Читай так: «Создай виджет `Center`. Его параметр `child` (ребёнок) это виджет `Text` с надписью "Привет"».

- `Center(...)` это вызов конструктора, как `Foo(...)` в C++. Он создаёт объект.
- `child:` это **именованный параметр**. В C++ ты передавал бы аргументы по порядку, а в Dart можно написать `имя: значение`. Читается как предложение.
- `Text('Привет')` это второй объект, он лежит **внутри** первого. Поэтому вложенность скобок и есть структура экрана.

`Center` умеет одну вещь: поставить своего ребёнка в центр. `Text` умеет одну вещь: показать строку. Из десятков таких простых кирпичиков собирается любой экран. Это как LEGO: у каждой детали одна простая функция.

### 7.3. `child` и `children`

Виджеты бывают двух видов по числу детей:

| Вид | Параметр | Примеры | Пояснение |
|---|---|---|---|
| Один ребёнок | `child:` | `Center`, `Padding`, `SizedBox`, `ConstrainedBox`, `SafeArea` | Оборачивает ровно один виджет и что-то с ним делает |
| Много детей | `children: [ ... ]` | `Column`, `Row`, `Stack` | Список виджетов, которые раскладываются в ряд, столбец или стопку |

Пример со многими детьми (упрощённо наш экран):

```dart
Column(
  children: [
    TextField(),
    SizedBox(height: 16),
    FilledButton(onPressed: ..., child: Text('Найти')),
  ],
)
```

Читается как «столбец из трёх вещей сверху вниз: поле, пустое место высотой 16, кнопка с надписью». Аналогия: многоэтажный дом, где `Column` это стояк, а `children` это квартиры по этажам.

### 7.4. Дерево нашего экрана

Всё вложенное друг в друга образует **дерево виджетов**. Вот дерево экрана поиска (актуально на этапе 5, файл [`lib/ui/search_screen.dart`](../lib/ui/search_screen.dart)):

```text
MaterialApp                              приложение целиком, тема, навигатор
└── SearchScreen                         наш экран
    └── Scaffold                         «каркас» экрана: верхняя панель + тело
        ├── AppBar                       верхняя полоса
        │   └── Text('Swifty Companion')
        └── SafeArea                     не лезть под вырез камеры и системные панели
            └── Center                   поставить ребёнка по центру
                └── SingleChildScrollView   разрешить прокрутку, если не влезает
                    └── ConstrainedBox      ограничить ширину до 480
                        └── Column          столбец
                            ├── TextField           поле ввода логина
                            ├── SizedBox(16)        пустой отступ
                            ├── FilledButton        кнопка
                            │   └── Text('Найти')   (или индикатор загрузки)
                            ├── SizedBox(16)        (только если есть ошибка запроса)
                            └── ErrorBanner         (только если есть ошибка запроса)
```

Таблица «кто здесь что делает» простыми словами:

| Виджет | Простыми словами | Аналогия |
|---|---|---|
| `MaterialApp` | Корень приложения: знает про тему (цвета), про навигацию и про то, какой экран первый | Здание целиком |
| `Scaffold` | Заготовка стандартного экрана: место под верхнюю панель, тело, а при желании кнопку «+» и боковое меню | Каркас квартиры с готовыми комнатами |
| `AppBar` | Верхняя полоса с заголовком и кнопкой «назад» (появляется сама, когда есть куда возвращаться) | Вывеска над входом |
| `SafeArea` | Отступает от «опасных» зон: вырез камеры, часы и батарея сверху, жестовая полоса снизу | Поля на листе при печати, чтобы принтер не обрезал текст |
| `Center` | Ставит ребёнка по центру доступной области | Табличка по центру стены |
| `SingleChildScrollView` | Если ребёнок выше экрана (например, вылезла клавиатура), включает прокрутку | Свиток: длиннее окна, но можно листать |
| `ConstrainedBox` | Не даёт ребёнку стать шире 480. На планшете поле не растянется на весь экран | Рамка, за пределы которой нельзя |
| `Column` | Столбец: дети сверху вниз | Стопка карточек |
| `TextField` | Поле ввода | |
| `SizedBox` | Пустая коробка заданного размера, часто как отступ | Распорка |
| `FilledButton` | Кнопка с заливкой | |

Здесь есть неочевидный момент: `SearchScreen` тоже виджет, он стоит в дереве выше `Scaffold`. Это наш собственный «кирпич», в котором мы спрятали всё, что внутри. Чем больше собственных виджетов, тем короче и читаемее каждый кусок. Поэтому на этапе 5 появились отдельные `ErrorBanner` и `ProfileAvatar`: большой экран разрезан на понятные детали.

### 7.5. Метод `build` и что такое `context`

У каждого нашего виджета есть метод `build`. Он отвечает на один вопрос: **«из каких виджетов состоит ты?»**

```dart
@override
Widget build(BuildContext context) {
  return Scaffold( ... );
}
```

- `build` возвращает описание (дерево виджетов). Он ничего не рисует сам.
- Flutter вызывает `build` **когда ему нужно**: при первом показе, при `setState`, при повороте экрана, при смене темы и так далее. Вызывай его сам руками нельзя и не нужно.
- Поэтому в `build` нельзя делать долгие и «тяжёлые» вещи (сетевые запросы, разбор больших файлов). Его могут вызывать десятки раз в секунду, например во время анимации. `build` должен быть быстрым и «чистым»: данные на входе, виджеты на выходе. Аналогия: чистая функция в C без побочных эффектов.
- `context` (`BuildContext`) это **«адрес» твоего виджета в дереве**. По нему Flutter находит соседей выше по дереву: тему, размеры экрана, навигатор. Пример: `Theme.of(context)` значит «найди ближайшую вверх по дереву тему». `Navigator.of(context)` значит «найди ближайший вверх навигатор». Аналогия: ты стоишь в многоэтажке, и спрашиваешь «где ближайший вверх по подъезду лифт?».

### 7.6. Виджет это неизменяемое описание. Что это значит и зачем

Виджеты во Flutter **неизменяемые** (все поля `final`). Ты не можешь взять уже созданный `Text` и поменять его надпись. Вместо этого ты создаёшь **новый** `Text` с другой надписью.

Звучит расточительно, но так и задумано. Аналогия: **чертёж и здание**.

- **Виджет** это чертёж. Бумага. Его можно выбросить и нарисовать заново почти бесплатно.
- **Реальный экран** это здание. Строить его дорого.

Flutter на самом деле хранит три связанных дерева:

| Дерево | Что это | Аналогия | Дорого ли пересоздавать |
|---|---|---|---|
| **Widget** | Описание «что нужно» | Чертёж | Очень дёшево, создаётся заново при каждом `build` |
| **Element** | «Прораб»: живой объект, который помнит, какой чертёж сейчас привязан к этому месту | Прораб на объекте | Живёт долго, сохраняется между перерисовками |
| **RenderObject** | То, что реально считает размеры и рисует пиксели | Готовая стена | Дорого, поэтому меняется только если что-то правда изменилось |

Когда ты вызвал `setState`, происходит так: появляется новый чертёж, прораб сравнивает его со старым («тип тот же? надпись другая?») и если меняется только надпись, он просто переписывает текст на готовой стене, а не ломает её и не строит заново. Знать эти три слова на защите достаточно как понимание «почему пересоздавать виджеты не страшно».

Практический вывод: **не бойся писать `const`** и пересоздавать виджеты. Ключевое слово `const` перед виджетом (`const SizedBox(height: 16)`) говорит Dart «этот объект никогда не меняется, создай его один раз при компиляции и переиспользуй». Flutter тогда даже не сравнивает такие части при перерисовке. Это бесплатная оптимизация. Анализатор сам подсказывает, где `const` можно добавить.

### 7.7. Как читать «лестницу» из скобок и не сойти с ума

Новичкам глаза режет, что код уезжает вправо. Несколько приёмов:

1. **Запятая в конце.** Видишь `),` в конце каждого параметра? Это не случайность. Запятая после последнего параметра заставляет форматтер (`dart format`) красиво разложить код по строкам. Без неё всё склеится в одну длинную строку. Если ставишь запятую, Android Studio сам делает красивые отступы.
2. **Читай сверху вниз как оглавление**: сначала самый внешний виджет, потом его `child`, потом `child` у того.
3. **Закрывающие скобки смотри по подсказкам IDE.** Android Studio рисует подпись справа от закрывающей скобки («// Column»). Можно включить в настройках Flutter (Editor → Code Style → Dart / Flutter UI Guides).
4. **Если вложенность стала глубже 4–5 уровней, выноси кусок в отдельный виджет.** Например, `ErrorBanner` вынесен в отдельный файл именно из-за этого.
5. **Правило «Wrap with…».** Нужно обернуть виджет в `Padding` или `Center`? В Android Studio нажми Alt+Enter на виджете, выбери «Wrap with Padding». Не надо печатать скобки руками.

### 7.8. Ловушки раздела

| Ловушка | Что видишь | Причина | Решение |
|---|---|---|---|
| Забыл запятую | Некрасивый форматтер, длинные строки | Нет «висящей» запятой | Поставить запятую и нажать форматирование |
| Забыл `child:` | Ошибка «The named parameter … isn't defined» или «positional argument» | Передал виджет без имени | Написать `child: ...` |
| Передал список в `child` | Ошибка типа | `child` ждёт один виджет, а не список | Для списка используй `children` и `Column`/`Row` |
| Тяжёлый код в `build` | Тормоза, лишние запросы | `build` вызывается часто | Выносить в `initState`, в функцию, вызываемую по нажатию |
| Попытка «изменить» готовый виджет | Не компилируется (`final`) | Виджеты неизменяемы | Менять **данные**, а не виджет; новый `build` создаст новый виджет |

## 8. `StatelessWidget` против `StatefulWidget` и `setState`

### 8.1. Вопрос, из которого всё растёт: «где хранить то, что меняется?»

Поле ввода. Пользователь набрал `jdoe`. Где хранится слово `jdoe`? Индикатор загрузки. Крутится он или нет? Сообщение об ошибке. Показано оно или нет?

Всё это называется **состоянием** (`state`): данные, которые живут во времени и меняются. Виджет-то неизменяемый (раздел 7.6), поэтому хранить изменяемые данные внутри него нельзя. Нужно место, которое **переживает перерисовки**. Для этого Flutter предлагает два вида виджетов.

### 8.2. Аналогия: открытка и доска с магнитами

- **`StatelessWidget` (без состояния)** это **открытка**. Напечатали, показали. Не помнит, не меняется сама. Хочешь другую картинку? Отдай другую открытку (новые данные от родителя). Формула: *картинка = f(данные, которые тебе передали)*. Ровно как чистая функция в C.
- **`StatefulWidget` (с состоянием)** это **доска с магнитами**. Доска стоит на месте, а магниты (данные) двигают. Двинул магнит, глянул на доску и увидел новую картину. Формула: *картинка = f(переданные данные, то, что я помню)*.

| | `StatelessWidget` | `StatefulWidget` |
|---|---|---|
| Хранит изменяемые данные | нет | да |
| Сам решает перерисоваться | нет | да, вызвав `setState` |
| Из чего состоит | один класс | **два** класса: виджет + его `State` |
| Пример у нас | `ProfileScreen`, `ErrorBanner`, `ProfileAvatar`, `ConfigErrorApp` | `SearchScreen` |
| Правило выбора | Всё, что можно сделать без памяти, делай без памяти | Только если реально есть меняющиеся данные |

Хорошее правило: **начинай со `StatelessWidget`**. Станет `StatefulWidget`, когда понадобится «помнить». Большинство экранов в Flutter сводятся к небольшому количеству stateful-виджетов и куче stateless-деталей.

### 8.3. Почему классов два (да, это странно, но есть причина)

Помнишь про чертёж и здание? Виджет это чертёж, выбрасываемый при каждой перерисовке. Если бы поле `_loading` лежало в самом виджете, оно бы **исчезало при каждом новом чертеже**. Нужно место, которое остаётся. Это объект `State`: он создаётся один раз и живёт, пока экран в дереве.

```text
SearchScreen          ← чертёж (виджет). Создаётся много раз. Хранит только то, что ему передали (repository).
   │ createState()
   ▼
_SearchScreenState    ← память экрана. Создаётся ОДИН раз. Хранит _loading, _fieldError, _requestError, контроллер.
```

### 8.4. Анатомия нашего `SearchScreen` по частям

```dart
class SearchScreen extends StatefulWidget {          // (1)
  const SearchScreen({super.key, required this.repository});
  final UserRepository repository;                   // (2)

  @override
  State<SearchScreen> createState() => _SearchScreenState();   // (3)
}

class _SearchScreenState extends State<SearchScreen> {          // (4)
  final TextEditingController _controller = TextEditingController();  // (5)
  bool _loading = false;                             // (6)
  String? _fieldError;
  ApiException? _requestError;

  @override
  void dispose() {                                   // (7)
    _controller.dispose();
    super.dispose();
  }

  Future<void> _submit() async { ... }               // (8)

  @override
  Widget build(BuildContext context) { ... }         // (9)
}
```

| № | Что это | Простыми словами |
|---|---|---|
| 1 | Класс виджета | «Чертёж экрана». Тонкий: только то, что ему передали снаружи |
| 2 | `repository` | Параметр от родителя. Не меняется. Внутри `State` достаётся как `widget.repository` |
| 3 | `createState` | «Создай мне память». Flutter вызывает один раз |
| 4 | Класс состояния | Тут вся «память» и логика. Подчёркивание делает его приватным (его видно только в этом файле) |
| 5 | Контроллер текста | Объект, который знает, что сейчас набрано в поле |
| 6 | `_loading`, `_fieldError`, `_requestError` | Наши «магниты»: идёт ли загрузка, какая ошибка у поля, какая у запроса |
| 7 | `dispose` | «Уборка перед уходом» (раздел 8.7) |
| 8 | `_submit` | Что делать по нажатию кнопки |
| 9 | `build` | Возвращает описание экрана **на основе текущих значений магнитов** |

Обрати внимание: в `build` ты не говоришь «покажи индикатор». Ты говоришь «**если** `_loading` истинно, в кнопке будет индикатор, **иначе** текст». Данные определяют картинку. Это и есть декларативность.

```dart
child: _loading
    ? const SizedBox(... CircularProgressIndicator ...)
    : const Text('Найти'),
```

`условие ? a : b` это тернарный оператор, такой же, как в C.

### 8.5. `setState`: что делает и чего НЕ делает

**Главное, что нужно запомнить:** смена переменной сама по себе **ничего не перерисовывает**. Flutter не следит за твоими переменными.

Представь, что ты написал:

```dart
_loading = true;        // без setState
```

Переменная стала `true`. Но `build` никто не вызвал, и на экране ничего не изменилось. Приложение «зависло» на старой картинке, хотя внутри данные уже новые. Это самая частая ошибка новичков.

Правильно:

```dart
setState(() {
  _loading = true;
});
```

`setState` делает две вещи: выполняет твою функцию (меняет переменные) и **помечает виджет «грязным»**, то есть говорит Flutter «перерисуй меня при ближайшем кадре». Кадр наступает через долю секунды, Flutter вызывает `build`, и ты видишь новые данные.

Аналогия из C: ты поменял глобальную переменную, но не вызвал `redraw()`. Данные новые, экран старый. `setState` это и есть `redraw()`, склеенный с изменением.

Несколько тонкостей:

- **`setState` не ждёт и не блокирует.** Он только записывает «перерисуй позже». `build` сработает чуть позже, не внутри `setState`.
- **Вызывай `setState` как можно «узко»**: внутри только смена данных, без тяжёлых вычислений и без `await`.
- **Менять поля без `setState`** технически можно, и они поменяются, но экран узнает об этом только при следующей случайной перерисовке. Не делай так.
- **`setState` нельзя вызывать из `build`**: получится бесконечный цикл («перерисуйся → перерисуйся → ...»). Flutter ругнётся ошибкой.

### 8.6. Симуляция 1: нажатие «Найти» с пустым полем

Актуальный код этапа 5:

```dart
final validation = validateLogin(raw);
if (validation != null) {
  setState(() {
    _fieldError = validation;
    _requestError = null;
  });
  return;
}
```

| Шаг | Что происходит | `_loading` | `_fieldError` | На экране |
|---|---|---|---|---|
| 0 | Экран открыт, поле пустое | false | null | Поле, кнопка «Найти» |
| 1 | Нажата кнопка, вызван `_submit()` | false | null | то же |
| 2 | `_loading` ложно, идём дальше. `validateLogin('')` возвращает `'Введите логин'` | false | null | то же |
| 3 | `setState`: `_fieldError = 'Введите логин'` | false | 'Введите логин' | то же (ещё не перерисовано!) |
| 4 | `return;` функция закончилась | false | 'Введите логин' | то же |
| 5 | Flutter вызывает `build` | false | 'Введите логин' | **Под полем красный текст** |

Видишь шаг 3→5? Данные уже новые, а картинка меняется чуть позже, когда Flutter сам вызовет `build`.

### 8.7. Симуляция 2: успешный поиск (по «кадрам»)

Допустим, ввели `jdoe` и нажали «Найти». Сеть отвечает за ~1 секунду.

| Момент | Событие | `_loading` | Кадр на экране |
|---|---|---|---|
| t=0 мс | Нажатие. `_submit` стартовал, проверка прошла | false | Кнопка «Найти» |
| t=0 мс | `setState(_loading = true)` | true | |
| t=16 мс | Flutter вызвал `build`: кнопка отключена, в ней индикатор, поле заблокировано | true | **Крутится индикатор** |
| t=16 … 900 мс | `await repository.fetchUser(...)`: функция «спит», но интерфейс не заморожен, индикатор анимируется, идут кадры | true | Крутится индикатор |
| t=~950 мс | Профиль получен. `if (!mounted) return;` экран ещё жив, идём дальше | true | |
| t=~950 мс | `setState(_loading = false)` | false | |
| t=~950 мс | `Navigator.push(ProfileScreen)` | false | Появляется экран профиля |
| позже | Пользователь нажал «назад» | false | Снова экран поиска, кнопка «Найти» |

Главная мысль: между шагами 2 и 3 (`await`) **`build` продолжает вызываться**, потому что `await` не блокирует поток. Поэтому индикатор крутится. В C ты сказал бы: «`sleep(1)` заморозил бы всё». Здесь `await` как «я пошёл ждать, разбуди меня, когда придёт ответ».

### 8.8. Жизненный цикл `State`: рождение, жизнь, смерть

У `State` есть несколько «событий», в которые Flutter вызывает методы:

| Метод | Когда вызывается | Сколько раз | Для чего |
|---|---|---|---|
| `initState()` | Сразу после создания, один раз | 1 | Подготовка: создать контроллеры, подписаться |
| `build()` | Когда надо нарисовать | много раз | Вернуть описание экрана |
| `dispose()` | Перед уничтожением | 1 | Освободить: контроллеры, подписки, таймеры |

Аналогия: **квартира**. `initState` это заселение, `build` это ежедневная жизнь (убрали, переставили), `dispose` это выселение с отключением газа и воды. Если съехал и оставил газ включённым, получится утечка (в нашем случае утечка памяти).

У нас `TextEditingController` создаётся как поле (`final _controller = TextEditingController();`), а освобождается в `dispose`. Это пара «взял / вернул», как `malloc`/`free` в C. Забыл `dispose`, и контроллер висит в памяти после закрытия экрана.

Есть ещё свойство **`mounted`**: «мой `State` ещё привязан к дереву?». После `dispose` оно становится `false`.

### 8.9. Почему после `await` нужен `if (!mounted) return;`

Сценарий-катастрофа:

1. Нажал «Найти», запрос ушёл (идёт 15 секунд, сеть плохая).
2. Пользователь потерял терпение и закрыл приложение или вышел с экрана.
3. Экран уничтожен (`dispose` вызван, `mounted == false`).
4. Через 15 секунд ответ пришёл, и код продолжает работать после `await`.
5. Без защиты он вызывает `setState` или `Navigator.of(context)` у мёртвого экрана. Это ошибка: `setState() called after dispose()`.

Решение:

```dart
final profile = await widget.repository.fetchUser(raw);
if (!mounted) {
  return;               // экрана нет, ничего не делаем
}
setState(() => _loading = false);
```

Правило из одной строки: **после каждого `await`, перед использованием `context` или `setState`, проверяй `mounted`**. Анализатор тоже напомнит (правило `use_build_context_synchronously`).

### 8.10. Откуда берутся данные: `widget.repository` и параметры

Внутри `State` к полям «чертежа» обращаются через `widget.`: `widget.repository`. Это потому что `State` и виджет разные объекты. Данные, которые приходят от родителя, доступны через `widget`, а данные, которые экран помнит сам, это поля `State`.

### 8.11. Ловушки раздела

| Ловушка | Симптом | Причина | Решение |
|---|---|---|---|
| Поменял поле без `setState` | Данные новые, экран старый | Flutter не следит за переменными | Оборачивать изменение в `setState` |
| `setState` в `build` | Ошибка, бесконечный цикл | `build` вызывает перерисовку, которая вызывает `build` | Менять состояние только в обработчиках событий |
| `setState` после `dispose` | `setState() called after dispose()` | Асинхронный код дожил до смерти экрана | `if (!mounted) return;` после `await` |
| Забыл `dispose` контроллера | Утечка памяти | Контроллер остаётся жить | Освобождать в `dispose` |
| Кладёшь изменяемые поля в `StatelessWidget` | Анализатор ругается (`must_be_immutable`) | Виджет неизменяем | Сделать `StatefulWidget` |
| Огромный `build` на 300 строк | Не разобрать | Всё в куче | Выносить части в отдельные виджеты |
| `await` внутри `setState` | Ошибка (колбэк должен быть синхронным) | `setState` не ждёт | `await` до `setState`, потом короткий `setState` |
| Двойное нажатие кнопки | Два запроса | Пока идёт запрос, кнопка активна | `if (_loading) return;` и отключение кнопки |

**Альтернативы `setState`** см. [раздел 12](#12-альтернативы-которые-мы-не-берём-и-почему).

## 9. Навигация: стек экранов

### 9.1. Аналогия: стопка тарелок

`Navigator` держит экраны в **стопке** (как `std::stack` в C++ или стек вызовов функций):

- `push` кладёт новую тарелку сверху. Пользователь видит верхнюю.
- `pop` снимает верхнюю. Под ней оказывается предыдущая, ровно в том состоянии, в каком мы её оставили.

Видна всегда только верхняя тарелка, а остальные лежат под ней и ждут. Это ещё и объясняет, почему «назад» работает бесплатно.

### 9.2. Код и разбор по частям

```dart
await Navigator.of(context).push(
  MaterialPageRoute<void>(
    builder: (_) => ProfileScreen(profile: profile),
  ),
);
```

| Часть | Что значит |
|---|---|
| `Navigator.of(context)` | «Найди ближайший вверх по дереву навигатор» (он создан `MaterialApp`) |
| `.push(...)` | «Положи в стопку этот маршрут» |
| `MaterialPageRoute` | «Маршрут в стиле Material»: даёт анимацию перехода и жест «назад» на Android |
| `<void>` | Тип значения, которое экран вернёт при закрытии. `void` = ничего |
| `builder: (_) => ProfileScreen(...)` | Функция, которая **создаёт** экран, когда он понадобится. `_` это «параметр мне не нужен» (там `context`) |
| `await` | Дождаться, пока экран профиля **закроют** |

### 9.3. Симуляция стека

| Действие | Стек (снизу вверх) | Что видит пользователь |
|---|---|---|
| запуск | `SearchScreen` | Поиск |
| `push(ProfileScreen)` | `SearchScreen`, `ProfileScreen` | Профиль |
| «назад» (стрелка в AppBar, системный жест или кнопка) | `SearchScreen` | Поиск |

Что это значит для задания: требование «вернуться на первый экран» выполняется само. Под профилем в стопке остался `SearchScreen` вместе со своим `State`: тот же введённый текст, те же поля. Нам не нужно писать код «вернуться».

### 9.4. Кто вызывает `pop`

- Стрелка в `AppBar`: `Scaffold` сам ставит её, если под ним есть другой экран.
- Системный жест / кнопка «назад» Android.
- Руками: `Navigator.of(context).pop()` (нам пока не нужно).

### 9.5. Передача данных и возврат результата

Вперёд данные передаются **параметром конструктора**: `ProfileScreen(profile: profile)`. Экран профиля получил уже готовый `UserProfile`, ему не нужно знать про сеть. Назад значение можно вернуть через `pop(значение)`, тогда `await push(...)` его получит. У нас тип `void`, возвращать нечего.

### 9.6. Ловушки навигации

| Ловушка | Что происходит | Решение |
|---|---|---|
| `push` после `await` без проверки `mounted` | Ошибка: контекст экрана мёртв | Проверка `mounted` (раздел 8.9) |
| Двойной `push` при двойном тапе | Два одинаковых экрана в стопке | Блокировка кнопки при загрузке |
| Передавать экрану логин и пусть сам грузит | Экран профиля тянет сеть, сложнее тестировать | Грузим до перехода, передаём готовый профиль (так сделано у нас) |
| Забыть, что под экраном живой старый | Старый экран ещё «слушает» | Это нормально; ради этого и нужен `dispose` |

## 10. Раскладка: `Column`, `Center`, `SafeArea` и другие

Это раздел про то, **как Flutter решает, где и какого размера что рисовать**. Из-за него чаще всего возникают красные полосы с ошибками. Разберём без паники.

### 10.1. Главное правило из одной строки

> **Ограничения идут вниз. Размеры идут вверх. Родитель решает, где стоит ребёнок.**

Аналогия: **начальник и подчинённый**.

1. Начальник (родитель) говорит подчинённому: «Бери под задачу место от 0 до 300 пикселей в ширину и от 0 до 800 в высоту». Это **ограничения** (constraints), они идут вниз.
2. Подчинённый (ребёнок) выбирает свой размер **внутри** этого диапазона и сообщает: «Мне нужно 120 × 40». Это **размер**, он идёт вверх.
3. Начальник решает, **в какой точке** поставить подчинённого. Подчинённый сам себя не позиционирует.

Если запомнить только это, 90% загадок раскладки решаются.

### 10.2. Наш экран на цифрах

Телефон, ширина 360 «логических пикселей», высота 800. Для простоты не учитываем статус-бар.

| Виджет | Какие ограничения получил | Что решил |
|---|---|---|
| `Scaffold` (body) | ширина 360, высота ~744 (экран минус AppBar) | занять всё |
| `SafeArea` | то же | отступил от вырезов, детям отдал чуть меньше |
| `Center` | ширина 0–360, высота 0–744 | разрешил ребёнку быть любым и поставил по центру |
| `SingleChildScrollView` (с отступом 24) | по ширине до 312 (360 минус 2×24), по высоте **без ограничения** | высота ребёнка как у ребёнка; если выше экрана, включается прокрутка |
| `ConstrainedBox(maxWidth: 480)` | ширина до 312 | 480 больше 312, значит остаётся 312 |
| `Column` (stretch) | ширина 312 | растянул детей на всю ширину 312 |
| `TextField`, `FilledButton` | ширина ровно 312 | заняли её |

На планшете шириной 800: после отступов доступно 752, а `ConstrainedBox` говорит «не больше 480». Получаем колонку 480 шириной, по центру. Так и работает «гибкая раскладка» из задания: никаких пикселей, прибитых гвоздями.

### 10.3. Основные виджеты раскладки

| Виджет | Зачем | Замечание |
|---|---|---|
| `Column` | Дети сверху вниз | Главная ось вертикальная |
| `Row` | Дети слева направо | Главная ось горизонтальная |
| `Center` | По центру | |
| `Padding` | Отступ вокруг | Или `padding:` у многих виджетов |
| `SizedBox` | Пустой блок или фиксированный размер | `SizedBox(height: 16)` как отступ |
| `SafeArea` | Не залезать под вырезы и системные панели | Всегда оборачивай экраны |
| `SingleChildScrollView` | Прокрутка одного большого содержимого | Защита от «переполнения» |
| `ListView` | Длинный прокручиваемый список | Для списков проектов на этапе 6 |
| `ConstrainedBox` | Ограничить размер | У нас максимальная ширина |
| `Expanded` | Забрать **всё оставшееся** место внутри `Row`/`Column` | Только как ребёнок `Row`/`Column` |
| `Flexible` | Как `Expanded`, но можно быть меньше | |
| `Wrap` | Как `Row`, но переносит на новую строку, если не влезло | |

### 10.4. Главная и поперечная оси

У `Column` и `Row` есть две оси:

```text
Column:                          Row:
главная ось = вертикаль ↓        главная ось = горизонталь →
поперечная = горизонталь         поперечная = вертикаль
```

| Параметр | Что делает | Примеры значений |
|---|---|---|
| `mainAxisAlignment` | Как расположить детей **вдоль** главной оси | `start`, `center`, `end`, `spaceBetween`, `spaceEvenly` |
| `crossAxisAlignment` | Как расположить **поперёк** | `start`, `center`, `end`, `stretch` (растянуть) |
| `mainAxisSize` | Сколько места занять вдоль главной оси | `max` (всё доступное, по умолчанию), `min` (только сколько нужно детям) |

У нас `mainAxisSize.min`: колонка не растягивается на всю высоту, а берёт только нужное, и `Center` ставит её по центру. А `crossAxisAlignment.stretch` растягивает поле и кнопку по ширине колонки.

### 10.5. `Expanded`: делим оставшееся место

```dart
Row(
  children: [
    SizedBox(width: 120, child: Text('Email')),   // 120 пикселей
    Expanded(child: Text('jdoe@example.com')),     // всё остальное
  ],
)
```

`Row` сначала даёт место ребёнку фиксированной ширины (120). Остаток (например, 192) отдаёт `Expanded`. Если текст длинный, он **переносится** внутри `Expanded` вместо того, чтобы вылезти за экран. Именно так сделан `_InfoRow` на экране профиля. Без `Expanded` длинный адрес почты вылез бы за край, и ты увидел бы жёлто-чёрную полосу.

### 10.6. Прокрутка: когда нужна

Если содержимое выше экрана (вылезла клавиатура, повёрнули телефон, огромный шрифт), без прокрутки получится **overflow**. С `SingleChildScrollView` содержимое просто можно листать. Это не «опция на потом», это страховка от самого частого дефекта.

### 10.7. Три знаменитые ошибки раскладки и как их читать

**1. `A RenderFlex overflowed by N pixels on the bottom/right`** (жёлто-чёрная полоса).
Содержимое не влезло. *Лечение:* обернуть в `SingleChildScrollView` (если прокрутка уместна), либо дать тексту `Expanded`/`Flexible`, либо сократить содержимое.

**2. `Vertical viewport was given unbounded height`** (`ListView` внутри `Column`).
`ListView` хочет быть настолько высоким, насколько ему нужно, а `Column` не ограничивает высоту детей. Два «бесконечных» подряд, и Flutter сдаётся. *Лечение:* обернуть `ListView` в `Expanded` (тогда у него будет ограничение «оставшееся место») или в `SizedBox` с высотой.

**3. `RenderBox was not laid out` / `BoxConstraints forces an infinite width`**.
Виджет внутри `Row` хочет бесконечную ширину (классика: `TextField` прямо в `Row`). *Лечение:* обернуть в `Expanded` или в `SizedBox` с шириной.

Общий рецепт чтения таких ошибок: найди в тексте первую строку со своим файлом (`lib/ui/...`), посмотри номер строки и подумай «какие ограничения здесь пришли сверху?».

### 10.8. Ловушки раскладки и размеров шрифта

| Ловушка | Что видишь | Решение |
|---|---|---|
| Фиксированные размеры в пикселях | На другом телефоне всё поплыло | Давать гибкие размеры, максимум ширины через `ConstrainedBox` |
| Большой системный шрифт | Текст вылезает | Использовать `Expanded`/`Flexible`, `SingleChildScrollView` |
| Нет `SafeArea` | Контент под вырезом камеры | Оборачивать |
| `Expanded` вне `Row`/`Column` | Ошибка `ParentDataWidget` | Использовать только как прямого ребёнка |
| Горизонтальный поворот | Не влезает по высоте | Прокрутка |

## 11. Hot reload и hot restart

Ты уже знаешь, что при разработке не нужно пересобирать приложение после каждой правки. Есть три уровня:

| | Hot reload (молния, `r`) | Hot restart (`R`) | Полный перезапуск (Stop → Run) |
|---|---|---|---|
| Что делает | Подкладывает новый код в работающее приложение | Перезапускает Dart-часть с нуля | Пересобирает и ставит приложение заново |
| Скорость | доли секунды | секунды | десятки секунд |
| Состояние (`State`, введённый текст, открытый экран) | **сохраняется** | сбрасывается | сбрасывается |
| Когда использовать | Меняешь вёрстку, цвета, тексты в `build` | Меняешь `main()`, инициализацию, поля `State`, `initState`, глобальные переменные | Меняешь ассеты (`.env`), `pubspec.yaml`, Android-часть (манифест) |

**Для этого проекта:**

- `.env` лежит в ассетах, а они читаются при сборке. Изменил `.env`? **Полный перезапуск** (Stop, затем Run). Hot reload и даже hot restart не помогут.
- Поменял `pubspec.yaml` (добавил пакет)? `flutter pub get` и полный перезапуск.
- Поменял `AndroidManifest.xml`? Полный перезапуск (так мы добавляли разрешение INTERNET).
- Поменял код `build` или текст? Hot reload.

Типичная ловушка: «я поменял, а ничего не изменилось». Чаще всего потому что поменял то, что инициализируется один раз (`initState`, поле `State`, `main`). Тогда нужен hot restart.

## 12. Альтернативы, которые мы не берём (и почему)

| Что | Альтернативы | Почему не берём |
|---|---|---|
| Состояние | `Provider`, `Riverpod`, `Bloc` | Проект на два экрана; `setState` проще объяснить на защите. Тянуть библиотеку, которую пришлось бы обосновывать, нет смысла |
| Навигация | `go_router`, `Navigator 2.0` | Нужен один переход вперёд-назад; обычный `Navigator.push` достаточен |
| Разбор JSON | `json_serializable`, `freezed` (кодогенерация) | Скрытые поля, `"hidden"` и несколько курсов требуют ручной логики; кодогенерация усложнит сборку и объяснение |
| Сеть | `dio` | У `http` меньше возможностей, но для двух запросов хватает; проще тестировать через `MockClient` |
| Загрузка | `FutureBuilder` | Хуже подходит, когда нужна кнопка с блокировкой и повторами |

Если на защите спросят «почему не X?», ответ в этом духе: «задача маленькая, лишняя зависимость не окупается».

## 13. Упражнения

Выполняй после того, как приложение запустится на телефоне. Это закрепляет `setState`, hot reload и раскладку. Для каждого написано, что ты должен увидеть.

1. **Цвет.** В `SwiftyApp` замени `Colors.indigo` на `Colors.teal` и сделай hot reload. *Ожидание:* кнопка и AppBar поменяли оттенок, введённый текст остался (состояние сохранилось).
2. **Счётчик.** В `_SearchScreenState` добавь поле `int _tries = 0;`, в начало `_submit` добавь `setState(() => _tries++);`, а под кнопкой выведи `Text('Попыток: $_tries')`. *Ожидание:* число растёт при каждом нажатии. Потом убери `setState` и оставь просто `_tries++;`, понаблюдай, что число на экране не обновляется (хотя внутри растёт). Это наглядное доказательство раздела 8.5.
3. **Ширина.** Измени `maxWidth: 480` на `200` и поверни телефон. *Ожидание:* поле узкое и по центру. Верни обратно.
4. **Крупный шрифт.** Включи в настройках Android крупный размер шрифта. Пройди оба экрана. *Ожидание:* ничего не вылезает (есть прокрутка и `Expanded`). Если что-то съехало, пришли скриншот.
5. **Ломаем тесты.** В `validateLogin` верни `null` всегда и запусти `flutter test`. *Ожидание:* упадут тесты логина и экрана поиска (про пустой ввод). Подумай, почему именно они. Верни обратно (`git checkout lib/core/login.dart`).
6. **Забытый `dispose`.** Закомментируй `_controller.dispose();` и запусти приложение. Ничего не упадёт, и в этом подвох: утечки тихие. Верни строку на место. Вывод: часть ошибок не видна глазами, и о них надо знать заранее.
7. **Вопрос себе:** что произойдёт, если вынести `_loading = true;` из `setState`? Подумай, потом проверь в приложении.

Если застрянешь, пиши, разберём.
