## 2. Теория: слои и зачем они

```text
Экран            ← знает только про UserRepository и ApiException
  └─ UserRepository    логин → UserProfile (проверка, имена, превращение JSON в модель)
       └─ ApiClient          адрес → JSON-объект (токен, повтор после 401, коды ответа)
            ├─ TokenService       выдаёт токен
            └─ http.Client        настоящая сеть (в тестах MockClient)
```

Каждый слой знает только о соседе под собой и решает **одну** задачу.

| Слой | Знает про | Не знает про |
|---|---|---|
| `UserRepository` | логины, `UserProfile`, что профиль живёт по адресу `/v2/users/<логин>` | заголовки, токены, коды ответа |
| `ApiClient` | HTTP: заголовки, коды, повтор, JSON-объект | что за JSON и что с ним делать |
| `TokenService` | как получить и хранить токен | какие запросы им пользуются |

**Зачем разделять.** Когда понадобится второй запрос (например, список проектов), он добавится в репозиторий, а `ApiClient` и `TokenService` не изменятся. Экран не придётся трогать при смене адреса или формата. Каждый слой тестируется отдельно: репозиторий без знания про заголовки, клиент без знания про модели.

Паттерн «репозиторий» это общепринятая прослойка между приложением и источником данных (сеть, база, файл). Для двух экранов он выглядит избыточным, но стоит недорого и даёт то самое разделение.

**Контракт ошибок.** Репозиторий бросает **только** `ApiException` (см. [docs/07](07-token-service.md), раздел 7). Это значит: на экране достаточно одного `try ... on ApiException catch (e)`, и `switch` по `sealed`-классу гарантирует учёт всех видов. Ни `FormatException`, ни `SocketException`, ни `TimeoutException` наружу не выходят.

## 3. Запрос: адрес, метод, заголовки

```text
GET https://api.intra.42.fr/v2/users/<логин>
Authorization: Bearer <токен>
Accept: application/json
```

- **GET**, потому что читаем данные и ничего не меняем.
- **`Authorization: Bearer <токен>`** так сервер узнаёт, что запрос от авторизованного приложения.
- **`Accept: application/json`** просим JSON (хорошая привычка, сервер и так отдаёт его).

### 3.1 Как собирается адрес и почему не строкой

Наивный способ: `Uri.parse('https://api.intra.42.fr/v2/users/$login')`. Если пользователь введёт `a?b` или `../me`, часть его ввода станет **частью структуры адреса** (начнётся query, путь «поднимется» на уровень выше). Это называется инъекцией в адрес.

Мы собираем адрес так:

```dart
Uri(scheme: 'https', host: apiHost, pathSegments: ['v2', 'users', login])
```

`Uri` кодирует **каждую часть пути отдельно**. Результаты (проверены тестом):

| Часть пути | В адресе | Что видит сервер |
|---|---|---|
| `jdoe` | `jdoe` | обычный логин |
| `a b/c?d` | `a%20b%2Fc%3Fd` | одна часть пути с пробелом, слэшем и вопросом внутри |

Это вторая линия защиты. Первая: проверка логина на экране и в репозитории ([docs/05](05-config-and-skeleton.md), раздел 4).

## 4. Повтор после 401

Иногда сервер отвергает токен раньше срока (отозвали, ошибка часов, токен истёк «в пути»). Тогда `ApiClient` делает ровно один повтор:

```dart
var token = await _tokenService.getToken();
var response = await _get(uri, token);
if (response.statusCode == 401) {
  _tokenService.invalidate(token);
  token = await _tokenService.getToken();
  response = await _get(uri, token);
}
return _handle(response);
```

### 4.1 Симуляция (тест `401, затем 200`)

| Шаг | Что происходит | Токен в памяти | Запросов токена | Запросов профиля |
|---|---|---|---|---|
| 1 | `getToken()`: памяти пусто → запрос токена | `tok-1` | 1 | 0 |
| 2 | GET профиля с `Bearer tok-1` → **401** | `tok-1` | 1 | 1 |
| 3 | `invalidate('tok-1')`: стирает `tok-1` | пусто | 1 | 1 |
| 4 | `getToken()` → запрос токена | `tok-2` | 2 | 1 |
| 5 | GET профиля с `Bearer tok-2` → **200** | `tok-2` | 2 | 2 |
| 6 | разбор JSON, результат вызывающему | `tok-2` | 2 | 2 |

### 4.2 Если и новый токен отвергнут

Шаги 1–4 те же. Шаг 5 даёт снова **401**. Дальше повтора **нет**: сервер отвергает свежий токен, значит, проблема не в токене (например, ключи приложения отозваны). Выбрасывается `AuthException`. Тест `два 401 подряд` убеждается, что запросов профиля было **ровно два**, а не больше. Бесконечные повторы бьют по лимитам API и подвешивают интерфейс.

### 4.3 Параллельные запросы и повтор

Если два запроса ушли с `tok-1` и оба получили 401, первый вызовет `invalidate('tok-1')` и запросит токен. Второй вызовет `invalidate('tok-1')` ещё раз: токен уже `tok-2`, поэтому `invalidate` ничего не стирает (см. [docs/07](07-token-service.md), раздел 6). И запрос токена в этот момент уже «в полёте», так что второй вызов `getToken()` присоединится к нему (раздел 4 того же документа). Итог: **один** новый токен на двоих.

## 5. Коды ответа → ошибки

Для запроса профиля (`ApiClient._handle`):

| Код | Исключение | Почему |
|---|---|---|
| 200 | результат | разбор тела как JSON-объекта |
| 401 (после повтора) | `AuthException` | токен отвергнут дважды, дело в ключах |
| 404 | `NotFoundException` | логин не найден: **главный пользовательский случай** |
| 429 | `RateLimitException(retryAfter)` | лимит запросов; `Retry-After` читаем, если он есть |
| 5xx | `ServerException` | сервер сломан или недоступен |
| 403 и всё остальное | `UnexpectedResponseException` | см. ниже |
| не JSON, не объект, не UTF-8 | `UnexpectedResponseException` | |
| нет сети, DNS, обрыв | `NetworkException` | |
| нет ответа за 15 с | `NetworkException.timeout()` | |

**Почему 403 не `AuthException`.** Для токен-эндпоинта 403 действительно означает «вы не авторизованы» ([docs/07](07-token-service.md)). Для запроса профиля 403 может означать, что именно к **этому** пользователю доступа нет, и текст «проверьте ключи в .env» был бы ложным. Мы не знаем, как API 42 использует 403, поэтому показываем нейтральное «неожиданный ответ». Это открытый вопрос ([раздел 14](#14-открытые-вопросы)).

Различия с токен-эндпоинтом:

| Код | Токен-эндпоинт | Запрос профиля |
|---|---|---|
| 400, 401 | `AuthException` | (401: повтор, потом `AuthException`; 400: `Unexpected`) |
| 403 | `AuthException` | `UnexpectedResponseException` |
| 404 | `UnexpectedResponseException` | `NotFoundException` |

## 6. Ловушка с кодировкой: почему `bodyBytes`

В пакете `http` у ответа есть `response.body` (строка) и `response.bodyBytes` (сырые байты). По документации пакета, `body` декодируется по параметру `charset` заголовка `Content-Type`, а **если его нет, используется latin1**. Если сервер не напишет `charset=utf-8`, имя «José» превратится в «JosÃ©».

Мы декодируем так: `jsonDecode(utf8.decode(response.bodyBytes))`. Сырые байты читаем как UTF-8 сами: JSON по стандарту (RFC 8259) передаётся в UTF-8. Тест `тело читается как UTF-8 без указания charset` отдаёт «José Ñandú» без `charset` в заголовке.

Бонус: если пришли байты, не являющиеся корректным UTF-8, `utf8.decode` бросает `FormatException`, мы превращаем её в `UnexpectedResponseException`.

Это важно для проекта: в 42 учатся люди со всего мира, и в `displayname` бывают акценты и не только латиница.

## 7. Сеть и таймаут

`guardedRequest` в `http_helpers.dart`:

```dart
try {
  return await send().timeout(timeout);
} on TimeoutException { throw const NetworkException.timeout(); }
  on SocketException  { throw const NetworkException(); }
  on http.ClientException { throw const NetworkException(); }
```

- Запрос передаётся **функцией** (`() => _client.get(...)`), а не готовым `Future`: так исключение, брошенное при самом создании запроса, тоже попадёт под перехват.
- `SocketException` приходит из `dart:io` (нет сети, DNS). Пакет `http` на разных платформах иногда оборачивает его в `http.ClientException`, поэтому ловим оба.
- Таймаут 15 с на запрос. Ответ с профилем содержит десятки проектов и может весить сотни килобайт; на плохой сети 15 с могут оказаться мало. Значение параметризуется (`requestTimeout`), подберём на реальных запросах.
- `Future.timeout` лишь **перестаёт ждать**; сам запрос может ещё лететь. Для нас это безвредно.

## 8. Рефакторинг `TokenService`

Перехват сетевых ошибок, чтение `Retry-After` и разбор JSON нужны и токен-сервису, и клиенту API. Чтобы не копировать, они вынесены в `http_helpers.dart`, а `TokenService` стал короче.

| Было в `TokenService` | Стало |
|---|---|
| `try { ... } on TimeoutException ... on SocketException ... on ClientException ...` | `guardedRequest(() => _client.post(...), _requestTimeout)` |
| разбор `retry-after` вручную | `parseRetryAfter(response.headers)` |
| `jsonDecode(response.body)` (кодировка по умолчанию latin1) | `decodeJsonObject(response)` (UTF-8 явно) |
| `const apiBaseUrl = 'https://...'` в файле сервиса | `apiHost` в `api_constants.dart`, адрес собирается через `Uri.https(apiHost, '/oauth/token')` |

Поведение не изменилось: все 23 теста `token_service_test.dart` остаются прежними и должны пройти.

**Зачем это в документации.** Любой рефакторинг это риск; его снижает набор тестов, написанный *до* изменения. Так мы убедимся, что «ничего не сломали».

## 9. Репозиторий

```dart
Future<UserProfile> fetchUser(String rawLogin) async {
  if (validateLogin(rawLogin) != null) throw const NotFoundException();
  final login = normalizeLogin(rawLogin);
  final json = await _api.getJson(['v2', 'users', login]);
  try {
    return UserProfile.fromJson(json);
  } on FormatException {
    throw const UnexpectedResponseException();
  }
}
```

1. **Страховка по логину.** Экран уже проверяет ввод, но репозиторий не должен полагаться на то, что вызывающий не ошибся. Недопустимый логин не может существовать, значит, `NotFoundException` и **ни одного сетевого запроса** (тест проверяет счётчик запросов). Допущение о формате логина наше (`[a-z0-9_-]`), см. [раздел 14](#14-открытые-вопросы).
2. **Нормализация:** `normalizeLogin` (обрезка пробелов и нижний регистр) делается и здесь, а не только на экране.
3. **`FormatException` → `UnexpectedResponseException`.** `UserProfile.fromJson` бросает `FormatException`, если в ответе нет `login` ([docs/06](06-models.md), раздел 5.3). Репозиторий переводит её в `ApiException`, чтобы нарушить контракт («только `ApiException`») было нельзя.

## 10. Альтернативы и почему не они

| Подход | Суть | Почему не взяли |
|---|---|---|
| **Свой `ApiClient` + репозиторий (выбрано)** | десять строк на повтор, коды явно | Просто, полностью под контролем, нет лишних зависимостей, легко объяснить |
| `dio` с перехватчиками | токен и повтор после 401 «из коробки» | Замена `http` на `dio`: ещё одна зависимость, которую надо обосновать; для двух запросов избыточно |
| Обёртка-декоратор `AuthenticatedClient extends http.BaseClient` | повтор прячется внутри `send()`, экран и репозиторий вызывают обычный `get` | Красиво и возможно, но тело запроса можно прочитать только один раз (потоком), и повтор усложняется; наша версия повторяет явно |
| `retrofit` / `chopper` (генерация клиента по аннотациям) | описывается интерфейс, код генерируется | Генераторы кода, лишняя сложность на двух запросах |
| Результат вместо исключений (`Result<T>`/`Either`) | ошибки как значения, без `try/catch` | Хорошо и функционально, но в Dart принятый стиль это исключения; sealed-иерархия даёт такую же исчерпывающность |
| Один класс вместо клиента и репозитория | меньше файлов | Смешивает HTTP и доменную логику; хуже тестируется |
| Кэш профилей на диске | второй показ того же логина мгновенный | Данные устаревают, лишняя сложность, приватность (хранить чужие данные) |

## 11. Ловушки и хорошие практики

| Ловушка | Как обошли |
|---|---|
| Склейка адреса строкой, инъекция `?` и `/` | `Uri(pathSegments: ...)`, тест на `a b/c?d` |
| `response.body` с кодировкой по умолчанию latin1 | `utf8.decode(bodyBytes)` |
| Бесконечные повторы при 401 | повтор ровно один раз, тест на два 401 |
| «Забыли стереть плохой токен» перед повтором | `invalidate(token)`, тест проверяет, что второй запрос ушёл с `tok-2` |
| Тело `http.Response(String)` в тестах с кириллицей падает (latin1) | в тестах отдаём `Response.bytes(utf8...)` |
| 403 как «ключи неверные» | нейтральный `UnexpectedResponseException` |
| Лишний сетевой запрос на заведомо плохой логин | проверка в репозитории до запроса |
| Исключения низкого уровня просачиваются на экран | контракт «только `ApiException`», тесты |

Хорошие практики этапа: слои с одной задачей; внедрение зависимостей (клиент, токен-сервис, таймаут через конструктор); поддельный сервер вместо реального в тестах (быстро, детерминированно, не тратит лимиты); тестирование ветвей отказа (401 дважды, нет токена, битое тело) наравне с успехом; рефакторинг под защитой тестов; ни токен, ни секрет не попадают в логи и тексты ошибок.

Поддельный сервер (`FakeApi`) устроен как один `MockClient`, который отвечает на оба адреса: `/oauth/token` выдаёт токены по порядку, остальное идёт в функцию `onUser(запрос, номер_попытки)`, которую тест задаёт сам. Поэтому «первый раз 401, второй 200» записывается одной строкой.

**Чего тесты не доказывают:** что реальный API ведёт себя так же. Особенно сомнительны точные коды ошибок, наличие `Retry-After`, реальный размер и скорость ответа. Проверим на этапе 5.

## 15. Вопросы на защиту по этому этапу

- Как вы получаете данные студента? → `GET /v2/users/<логин>` с `Authorization: Bearer`, токен из `TokenService`.
- Что будет, если токен недействителен? → один повтор с новым токеном; если снова 401, понятная ошибка авторизации.
- Как вы различаете «логин не найден» и «нет сети»? → 404 это `NotFoundException`, сетевые сбои это `NetworkException`; тексты разные.
- Что будет при слишком частых запросах? → 429 это `RateLimitException`, учитываем `Retry-After`.
- Почему вы не клеите адрес строкой? → инъекция символов `?`, `/`; `Uri(pathSegments: ...)` кодирует части.
- Зачем `bodyBytes`, а не `body`? → кодировка по умолчанию latin1 ломает не-ASCII; JSON это UTF-8.
- Зачем репозиторий? → отделяет экран от HTTP и JSON; один контракт ошибок.
- Как вы тестировали сеть без интернета? → `MockClient` и поддельный сервер, 101 тест, мутационные проверки.
