## 2. Теория: из каких слоёв состоит окружение

Разработка на Flutter под Android это **стопка слоёв**, и ошибки почти всегда живут в каком-то одном из них. Когда что-то падает, первым делом нужно понять, на каком слое.

| Слой | Что это | Зачем нужен | Как ломается |
|---|---|---|---|
| **Flutter SDK** | Фреймворк (виджеты), движок отрисовки и консольная утилита `flutter` | Собирает и запускает приложение | Нет в `PATH`, устаревшая версия |
| **Dart SDK** | Компилятор и виртуальная машина языка Dart. Входит во Flutter, ставить отдельно не нужно | Выполняет и компилирует код | Редко: скачивается при первом запуске `flutter` |
| **Android SDK** | Набор инструментов Google для сборки под Android | Без него нельзя собрать APK | Не найден, нет компонентов, не приняты лицензии |
| ↳ `platform-tools` | В частности утилита **`adb`** (Android Debug Bridge) | Связь компьютера с телефоном: установка, отладка | Нет в `PATH`, нет прав на USB |
| ↳ `build-tools` | Инструменты упаковки APK | Сборка | Нет нужной версии |
| ↳ `platforms` | Библиотеки конкретной версии Android (API-уровня) | Компиляция под нужный API | Нет нужной платформы |
| ↳ `cmdline-tools` | Консольные утилиты, в том числе менеджер пакетов SDK | Установка и обновление компонентов, принятие лицензий | Отсутствует, лежит не в `latest/` |
| **JDK** (Java) | Среда для запуска Gradle | Gradle написан на Java/Kotlin и без неё не запустится | Не найдена или не та версия |
| **Gradle** | Система сборки Android | Из исходников делает APK | Долго скачивает зависимости, не хватает места |
| **IDE** (Android Studio) | Редактор с плагинами Flutter и Dart | Удобство: подсказки, запуск кнопкой | Плагин несовместим с версией IDE |
| **Устройство** | Реальный телефон | Здесь приложение запускается | Не авторизован, кабель, права на USB |

**Ключевой вывод:** *Android Studio и Android SDK это разные вещи.* SDK нужен всегда, IDE нет: код можно писать в любом редакторе и запускать командой `flutter run`. Именно поэтому на кампусе возможен вариант «IDE тормозит, работаем из терминала».

**Что делает `flutter run`, по шагам:**

1. Утилита `flutter` вызывает Gradle.
2. Gradle (на Java) собирает Android-часть (папка `android/`), подтягивает зависимости и упаковывает движок Flutter и Dart-код в **APK**.
3. Через `adb` APK устанавливается на телефон, и приложение запускается.
4. `flutter` остаётся запущенным и держит с приложением связь по отладочному каналу. Через неё работает hot reload.

## 3. Особенности кампуса

### 3.1. Что общее между машинами, а что своё

Это самое важное свойство кампуса, и из-за него в первой версии этого документа накопился беспорядок: он описывал «ту самую машину», а машин много.

| Что | Общее для всех машин? | Что из этого следует |
|---|---|---|
| Домашняя папка `~`: проект `~/Projects/swifty-companion`, `.git`, `.env`, `~/.zshrc` | **Да** (со слов владельца: проект лежит в одном и том же пути на любой машине) | Исходники, секреты и строки `PATH` не надо переносить. Но и состояние рабочей папки (`git status`, `pubspec.lock`, ссылка `build`) **общее**: что сделали на одной машине, видно на другой |
| `~/goinfre` | **Нет**, это локальный том конкретной машины и он периодически чистится | Flutter SDK, Android SDK, кэш Gradle, файл лимитов памяти Gradle (раздел 20.1) и цель ссылки `build` лежат здесь и **на каждой машине свои**; на новой машине их нет |
| Версия Flutter | Нет, она зависит от даты клонирования на этой машине | Раздел 4.5 |

Типичная ловушка: в общей папке проекта осталась ссылка `build -> ~/goinfre/swifty_build`, а на новой машине цели у неё нет. Раздел 21.5 разбирает это подробно.

### 3.2. Ограничения

| Ограничение | К чему приводит | Как живём |
|---|---|---|
| Нет `sudo` | Нельзя ставить пакеты системным менеджером (например, `ninja-build`) | Ставим всё в пользовательские папки |
| Папка `goinfre` | Места много, но она **периодически чистится** | Хранить там тяжёлое (SDK, кэши), а исходники держать вне goinfre и в GitHub |
| Слабые машины | Эмулятор Android зависает, а то и перезагружает компьютер | Используем реальный телефон по кабелю |
| Маленькая квота в домашней папке (около 4,7 ГБ) | Кэш Gradle и папка `build` (больше гигабайта) не помещаются | Переносим кэш Gradle и `build` в goinfre (раздел 10 и 20.2) |
| Мало оперативной памяти (7,6 ГиБ на машине 2) | Gradle с настройками по умолчанию (до 8 ГБ) может подвесить машину | Ограничиваем память Gradle (раздел 20.1) |

Подробности по чистке goinfre и порядок восстановления в разделе [16](#16-восстановление-после-чистки-goinfre).

## 4. Шаг 1. Flutter SDK и переменная PATH

### 4.1 Установка

```bash
git clone https://github.com/flutter/flutter.git -b stable ~/goinfre/flutter
```

Клонируем репозиторий Flutter сразу в канал `stable`. Преимущество такого способа в том, что обновляется он командой `flutter upgrade`. Альтернатива: скачать архив со страницы установки. Тогда обновлять придётся вручную.

### 4.2 Что такое PATH и зачем он нужен

`PATH` это список папок, в которых оболочка ищет программы, когда ты набираешь команду. Папки Flutter там нет, поэтому `flutter` не находится. Нужно добавить `~/goinfre/flutter/bin` в этот список. Чтобы это работало в каждом новом терминале, строку прописывают в файл `~/.zshrc`, который zsh читает при запуске.

### 4.3 Правильная команда

```bash
echo 'export PATH="$HOME/goinfre/flutter/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc
which flutter
```

Разбор:

- **Одинарные кавычки** вокруг строки обязательны: тогда `$HOME` и `$PATH` не раскрываются сейчас, а записываются в файл как есть и раскрываются при каждом запуске оболочки.
- **`>>` дописывает** в конец файла. Одинарный **`>` перезаписал бы весь файл** и стёр твои настройки. Не перепутай.
- **`source ~/.zshrc`** применяет изменения в текущем терминале (в новых терминалах они подхватятся сами).
- **`which flutter`** должен показать путь внутри `goinfre`. Пустой вывод значит, что строка не дописалась или в пути опечатка.

### 4.4 Что у нас пошло не так (две ошибки в одном месте)

Первая инструкция содержала комментарий в той же строке (`export PATH=... # добавь в ~/.zshrc`), и мы получили:

```text
export: not valid in this context: /home/vdarsuye/.zshrc
zsh: permission denied: /home/vdarsuye/.zshrc
```

**Причина первой ошибки.** В интерактивном zsh символ `#` по умолчанию **не начинает комментарий** (за это отвечает опция `interactive_comments`, она выключена). Всё после `#` zsh передал команде `export` как аргументы, в том числе слово `~/.zshrc`. `export` попытался сделать переменной окружения путь к файлу, а это не имя переменной, отсюда «not valid in this context».
**Урок:** в команды, которые вставляешь в терминал, комментарии на той же строке не писать.

**Причина второй ошибки.** Набрав просто `~/.zshrc`, ты попросил zsh **выполнить файл как программу**, а у файла нет права на исполнение, отсюда «permission denied». Файлы настроек не запускают, а читают (`cat`) или дописывают (`>>`).

### 4.5 Версия Flutter у каждой машины своя

Команда из 4.1 клонирует канал `stable` **на момент клонирования**. Поэтому на одной машине оказалась версия 3.47.7, а на другой, склонированной позже, 3.50.0. Эта разница уже трижды давала о себе знать:

| Что проявилось | Где разобрано |
|---|---|
| Android Gradle Plugin 9.1.0 стал «слишком старым» для Flutter 3.50 (нужен 9.1.1) | [docs/17](17-material-ui-migration.md), раздел 11 |
| Импорты `package:flutter/material.dart` устарели в 3.50 (29 замечаний анализатора) | [docs/17](17-material-ui-migration.md) |
| `pubspec.lock` меняется при смене машины | [docs/02](02-git-and-secrets.md), раздел 13 |

**Что делать.** Знать версию: `flutter --version`. Если на защите ты работаешь на новой для себя машине, первым делом сверь версию с последней проверенной (это 3.50.0, проект проверен на ней и на 3.47.7). Закрепить версию можно, но мы так не делаем: раздел 17.4.

**Риск, о котором стоит помнить:** у проверяющего версия Flutter может оказаться ещё новее. Новые версии поднимают минимальные версии инструментов сборки и со временем удаляют устаревшее, поэтому проект могут ждать те же сюрпризы, что мы уже видели. Поэтому полезно держать проект на актуальных версиях (мы поэтому и мигрировали на `material_ui`).

## 5. Шаг 2. flutter doctor: как читать вывод

`flutter doctor` проверяет все слои из раздела 2 и показывает, что в порядке, а что нет. Версия `flutter doctor -v` показывает подробности (пути, версии).

Первый запуск скачивает Dart SDK и собирает инструмент `flutter`, это нормально.

### 5.1 Первый вывод (до настройки Android)

| Пункт | Статус | Смысл |
|---|---|---|
| Flutter | ✓ | SDK найден |
| Android toolchain | ✗ | Не найден Android SDK, **главная проблема** |
| Chrome | ✓ | Нужен для веб-сборок, нам не пригодится |
| Linux toolchain | ✗ | Не хватает `ninja`, см. ниже |
| Connected device | ✓ | Это были Chrome и Linux desktop, а не телефон |
| Network resources | ✓ | Сеть доступна |

### 5.2 Почему красный Linux toolchain мы игнорируем

Для сборки десктопной версии под Linux нужен `ninja`. Мы собираем приложение под Android, поэтому этот пункт не мешает работе. Установить `ninja` без `sudo` не получится, и нужды в нём нет. Проект создан с флагом `--platforms=android`, так что папки `linux/` в нём нет вообще.

### 5.3 Итоговый вывод (после настройки)

Всё зелёное, кроме Linux toolchain. В Android-разделе видно: SDK найден, платформа и build-tools на месте, Java найдена, лицензии приняты. Телефон отображается в «Connected device».

## 6. Шаг 3. Android SDK

### 6.1 Найти существующий SDK

Android Studio хранит путь в **Settings → Languages & Frameworks → Android SDK**, поле **Android SDK Location**. У нас SDK лежит в `~/goinfre/androidSDK` (в нём уже были `build-tools`, `emulator`, `licenses`, `platforms`, `platform-tools`, `sources`). Папка `emulator` лежит там просто потому, что компонент был установлен раньше: эмулятором мы не пользуемся.

### 6.2 Сказать Flutter, где SDK

```bash
flutter config --android-sdk "$HOME/goinfre/androidSDK"
```

### 6.3 Ловушка: две похожие настройки

У `flutter config` есть две разные опции, и их легко спутать:

| Опция | На что указывает | Что внутри |
|---|---|---|
| `--android-sdk` | Папка **Android SDK** | `platform-tools`, `build-tools`, `platforms`, `cmdline-tools` |
| `--android-studio-dir` | Папка самой **IDE** | `bin/studio.sh`, `jbr/` и т. п. |

Мы по ошибке записали путь к **SDK** в `--android-studio-dir`, и `flutter doctor` ответил:

```text
Could not find the Android Studio installation at the manually configured path ...
```

Заодно в строке был символ `~` в кавычках, а **внутри кавычек оболочка тильду не раскрывает**, поэтому Flutter получил её как буквальный символ. Для настроек всегда пиши абсолютный путь или `"$HOME/..."` в двойных кавычках.

Исправление: сбросить неверную настройку.

```bash
flutter config --android-studio-dir ""
```

Команда без значения (`flutter config --android-studio-dir`) даёт ошибку `Missing argument for "--android-studio-dir"`. Нужна именно пустая строка, тогда вывод: `Removing "android-studio-dir" value.`

Ещё одна неточность по пути: мы сначала искали SDK в `goinfre/<логин>/androidSDK`, а настоящий путь был `goinfre/androidSDK`. Помогла простая проверка:

```bash
ls ~/goinfre/androidSDK
```

**Урок:** прежде чем прописывать путь в настройки, проверяй его командой `ls`.

### 6.4 `cmdline-tools` и лицензии

После настройки пути `flutter doctor` показал:

```text
✗ cmdline-tools component is missing.
✗ Android license status unknown.
```

а `flutter doctor --android-licenses` ответил `Android sdkmanager not found`. Это **один и тот же блокер**: лицензии принимает утилита `sdkmanager`, а она живёт в `cmdline-tools`, которых в SDK не было.

Нужно получить в SDK структуру **`cmdline-tools/latest/bin/sdkmanager`**. Если внутри `cmdline-tools` лежит не `latest`, а что-то другое, Flutter её не найдёт.

**Способ 1 (через Android Studio).** SDK Manager → вкладка **SDK Tools** → галочка **Android SDK Command-line Tools (latest)** → Apply. Если пункта не видно, нужно отключить «Hide Obsolete Packages». Следить, чтобы Android SDK Location в IDE совпадал с нашим `~/goinfre/androidSDK`.

**Способ 2 (вручную).** Скачать архив «Command line tools only» для Linux со страницы https://developer.android.com/studio#command-line-tools-only и разложить так:

```bash
cd ~/goinfre
mkdir -p cmdtools_tmp androidSDK/cmdline-tools
unzip commandlinetools-linux-*_latest.zip -d cmdtools_tmp
mv cmdtools_tmp/cmdline-tools androidSDK/cmdline-tools/latest
ls androidSDK/cmdline-tools/latest/bin
```

Последняя команда должна показать `sdkmanager`.

> На второй машине кампуса `cmdline-tools` ставили вручную (Способ 2: архив `commandlinetools-linux-*_latest.zip` и временная папка `cmdtools_tmp`). Какой способ использовался на первой машине, в записях не сохранилось. Полный чек-лист установки по частям: раздел 21.

После этого:

```bash
flutter doctor --android-licenses
flutter doctor -v
```

Вывод должен содержать `All Android licenses accepted.`

### 6.5 Предупреждение про устаревший sdkmanager

При принятии лицензий вывод содержал:

```text
WARNING: The SDK Manager CLI tool (sdkmanager) is deprecated. Android CLI will be used instead.
Warning: The --licenses option is no longer needed.
```

Это **информационное предупреждение**, а не ошибка. Google заменяет `sdkmanager` новой утилитой `android` (Android CLI), а лицензии к тому моменту уже были приняты (`All Android licenses accepted`). Ничего делать не нужно.

## 9. Шаг 6. Телефон вместо эмулятора

Эмулятор на машинах кампуса вешает систему, поэтому используем **реальный телефон** (Android, подключение кабелем).

### 9.1 Подготовка телефона

1. **Настройки → О телефоне** → семь раз нажать на **«Номер сборки»**: включится режим разработчика.
2. **Для разработчиков → Отладка по USB** включить.
3. Подключить кабелем. Кабель должен быть **для передачи данных**, а не только зарядки.
4. На экране телефона подтвердить запрос ключа RSA.

Что мы получили: телефон сразу появился в списке устройств Flutter как `SM A336B`, Android 16, архитектура `android-arm64`.

### 9.2 Откуда берётся ID устройства

В выводе `flutter devices` (и в `flutter doctor -v`) есть строка вида:

```text
SM A336B (mobile) • <ID_устройства> • android-arm64 • Android 16 (API 36)
```

Это **серийный номер телефона**. Он нужен в команде `flutter run -d <ID_устройства>`. Если подключён один телефон, ID можно не указывать: Flutter выберет его сам. ID нужен, когда устройств несколько (на кампусе в списке есть ещё Linux и Chrome).

### 9.3 adb и его PATH

`adb` (из `platform-tools`) **уже установлен** вместе с SDK, но его папки нет в `PATH`, поэтому команда `adb` не находилась. Тот же приём, что с Flutter:

```bash
echo 'export PATH="$HOME/goinfre/androidSDK/platform-tools:$PATH"' >> ~/.zshrc
source ~/.zshrc
which adb
adb devices
```

Статусы в `adb devices`:

| Статус | Значение | Что делать |
|---|---|---|
| `device` | Всё хорошо | Ничего |
| `unauthorized` | Телефон не подтвердил ключ | Подтвердить запрос на экране |
| `no permissions` | Нет прав на USB-устройство в Linux | Проблема прав на кампусе, нужен отдельный разбор |

Если `adb` ведёт себя странно, помогает перезапуск его фонового процесса:

```bash
adb kill-server
adb devices
```

### 9.4 Подводные камни

- **Samsung и защитные функции.** На телефонах Samsung (у нас `SM A336B` именно он) защитная функция **Auto Blocker**, если она включена, может блокировать установку приложений и команды по USB-кабелю. Если сборка дошла до установки и упала, подозрение первым делом на неё. Это предположение: у нас такой проблемы не возникло.
- **Беспроводная отладка** (Android 11+, `adb pair` и `adb connect`) есть как запасной вариант, но она работает только если Wi-Fi кампуса не изолирует клиентов друг от друга.
- **Режим USB** в шторке уведомлений: подходит «Передача файлов», но не «Только зарядка».

## 13. Потеря соединения и переподключение

В конце первого запуска терминал написал `Lost connection to device.` Приложение при этом **осталось на телефоне и работало**: оборвалась только отладочная связь с терминалом.

**Вероятная причина:** пока ты отходил, экран телефона погас, а Android (особенно Samsung) может усыпить USB-отладку или оборвать соединение. Точную причину мы не устанавливали.

**Способы переподключиться:**

| Способ | Команда | Когда |
|---|---|---|
| Запустить заново (надёжнее всего) | `flutter run` (или с `-d <ID_устройства>`) | Всегда подходит. Повторные сборки быстрее первой |
| Подключиться к уже запущенному | `flutter attach -d <ID_устройства>` | Только для debug-сборки и пока приложение живо на телефоне. Не нашёл процесс → запускай заново |
| Телефон не виден | `flutter devices`, затем `adb kill-server` и `adb devices` | Если список устройств пуст |

**Чтобы связь не рвалась:**

1. В «Для разработчиков» включить **«Не выключать экран»** (Stay awake): экран не гаснет, пока телефон на зарядке.
2. Проверить режим USB в шторке уведомлений.
3. При повторяющихся обрывах менять кабель или порт (дешёвые кабели и хабы так делают).
4. Не двигать телефон и кабель во время работы.

Повторный запуск после обрыва прошёл успешно (со слов владельца проекта, «всё работает»).

## 14. Hot reload

Пока `flutter run` работает, терминал принимает клавиши:

| Клавиша | Действие |
|---|---|
| `r` | **Hot reload**: подгружает изменённый код, состояние приложения **сохраняется** |
| `R` | **Hot restart**: перезапуск с нуля, состояние сбрасывается |
| `q` | Выход, приложение на телефоне завершается |
| `d` | Отсоединиться, оставив приложение запущенным |
| `h` | Список всех команд |

**Как проверить, что цикл работает:** запусти `flutter run`, открой `lib/l10n/app_strings_es.dart`, поменяй текст любой надписи на экране поиска (например, `loginLabel`), сохрани и нажми `r`. Если надпись на телефоне сменилась за секунду без пересборки, всё работает как надо. Если нет, нажми `R` (hot restart): надписи берутся из объекта, который создаётся при старте, и hot reload мог его не заметить (точное поведение для нашего случая не проверялось).

> Эта проверка заменила прежнюю: она предлагала менять `seedColor` в демо-приложении со счётчиком, а демо давно заменено нашим приложением.

**Теория:** hot reload возможен потому, что в debug-режиме Dart работает в виртуальной машине с JIT-компиляцией. Изменённые классы подгружаются в уже работающую машину, а дерево виджетов перестраивается. Состояние (значения в `State`) остаётся. Hot restart заново запускает программу, поэтому состояние теряется. В release-режиме (AOT) hot reload невозможен.

**Ограничения:** hot reload не подхватывает некоторые изменения (например, поменялось значение, которое вычисляется один раз при старте). В таких случаях нужен `R`.

## 16. Восстановление после чистки goinfre

Этот порядок нужен и после чистки `goinfre`, и на новой машине. В `goinfre` лежат тяжёлые компоненты, которых там тогда нет. Исходники проекта, `.env`, `.git` и `~/.zshrc` лежат в **общей домашней папке**, поэтому они на месте всегда (раздел 3.1). Порядок восстановления:

| 4 | Android SDK | Чек-лист 21.3 (по частям, без Android Studio) |

## 20. Кампус: память Gradle, квота home, `build` в goinfre, `flutter clean`

Этот раздел появился после реального дня на кампусе: комп завис посреди сборки, а `flutter clean` тихо сломал перенос `build`. Всё ниже проверено на машине с 7,6 ГиБ ОЗУ, 6 ядрами и домашней квотой около 4,7 ГБ.

### 20.1. Gradle по умолчанию просит больше памяти, чем есть на кампусе

Шаблон Flutter кладёт в `android/gradle.properties`:

```
org.gradle.jvmargs=-Xmx8G -XX:MaxMetaspaceSize=4G ...
```

Это **потолок**, а не расход: обычная сборка укладывается в 2–3 ГБ. Но чистая сборка (после очистки `build`, с распаковкой NDK и release-оптимизациями) может раздуться, и на 7,6 ГиБ система уходит в swap и замирает. Причина названа гипотезой: мы её не измеряли (`vmstat` во время зависания не снимали), но после ограничения памяти сборка прошла.

**Что сделали.** Настройки на уровне пользователя, без правки репозитория. Файл в `GRADLE_USER_HOME` (у нас `~/goinfre/.gradle`) приоритетнее проектного:

```bash
mkdir -p ~/goinfre/.gradle
cat > ~/goinfre/.gradle/gradle.properties <<'EOF'
org.gradle.jvmargs=-Xmx2g -XX:MaxMetaspaceSize=512m
org.gradle.workers.max=2
org.gradle.parallel=false
kotlin.daemon.jvmargs=-Xmx1g
EOF
```

| Строка | Смысл |
|---|---|
| `-Xmx2g` | куча Gradle до 2 ГБ вместо 8 |
| `MaxMetaspaceSize=512m` | метаспейс до 0,5 ГБ вместо 4 |
| `workers.max=2` | не больше двух параллельных рабочих |
| `parallel=false` | модули по очереди |
| `kotlin.daemon.jvmargs` | отдельный лимит Kotlin-демону: первая строка на него не действует |

**Риски.** Слишком мало памяти даёт `OutOfMemoryError` в Gradle: тогда поднять `-Xmx` до `3g`. Дома, где ОЗУ больше, этот файл не нужен.

**Как проверить, что настройка применилась.** Демон Gradle живёт только во время и некоторое время после сборки, поэтому проверка при незапущенной сборке выдаёт пустой вывод (это не ошибка). Быстрый способ поднять демона без сборки: `cd android && ./gradlew help`, затем `pgrep -af GradleDaemon | grep -o -- '-Xmx[0-9a-zA-Z]*'` (ожидаем `-Xmx2g`). Если вместо этого `-Xmx8G`, проверить `echo $GRADLE_USER_HOME`: в этом терминале переменная могла быть не задана.

**Как отличить нехватку памяти от упора в диск**, пока идёт сборка: во второй вкладке `vmstat 2`.

| Столбец | Тревожный признак | Значит |
|---|---|---|
| `si` / `so` | устойчиво больше нуля | кончилась память |
| `wa` | устойчиво больше 30–40 % | упёрлись в диск (например, распаковка NDK) |

При растущем `so` прерывай сборку (Ctrl+C) раньше, чем замёрзнет интерфейс. Запасные варианты: `flutter build apk --debug` (легче), либо собрать APK дома, а на кампусе делать только `flutter analyze` и `flutter test`, которым Android не нужен.

### 20.2. Домашняя квота и `build` в goinfre

Домашний раздел на кампусе маленький (около 4,7 ГБ), а папка `build/` проекта весит больше гигабайта. Решение: настоящая папка лежит в goinfre, а в проекте символическая ссылка.

```bash
mkdir -p ~/goinfre/swifty_build
ln -s ~/goinfre/swifty_build ~/Projects/swifty-companion/build
```

Ссылку нужно добавить в `.git/info/exclude` (локальный аналог `.gitignore`), чтобы она не попала в коммит.

**Ловушка: `flutter clean` удаляет ссылку, а не содержимое.** Для Flutter `build` это просто «папка по имени `build`»: ссылка исчезает, а настоящая папка в goinfre остаётся с гигабайтами старья. Следующая сборка тихо создаст **настоящий** `build` в home, и квота снова забита.

Правильно после clean:

```bash
cd ~/Projects/swifty-companion
rm -rf ~/goinfre/swifty_build/*
ln -s ~/goinfre/swifty_build build
flutter pub get
```

`ln -sfn` вместо `ln -s` безопаснее в скрипте: `-f` заменяет существующее, `-n` не даёт создать ссылку *внутри* целевой папки, если `build` уже ссылка. Альтернатива: вообще не вызывать `flutter clean`, а чистить только `rm -rf ~/goinfre/swifty_build/*` (ссылка остаётся).

Важно: NDK и кэш Gradle лежат в `~/goinfre/androidSDK` и `~/goinfre/.gradle`, то есть вне `build/`, и очистка `build` их не трогает. Долгая распаковка NDK при пересборке не повторяется.

### 20.3. Мусор в home: snap и кэши

Орфанные папки удалённых snap-приложений (`~/snap/<имя>`) занимают место, хотя самого приложения уже нет. Проверка: `snap list` и `du -h --max-depth=1 ~ | sort -h | tail`. Удалять только то, чего нет в `snap list`.

Если `~/.pub-cache` или другие кэши разрастаются, их можно перенести в goinfre переменной окружения (`PUB_CACHE`), но goinfre периодически чистят, и кэш придётся скачивать заново (раздел 16).

### 20.4. Подводные камни zsh при копировании команд

- Комментарии `# ...` в **интерактивном** zsh по умолчанию не комментарии: слова из них уходят в команду аргументами. Не копируй комментарии вместе с командой (или `setopt interactive_comments`).
- `!` в строке запускает подстановку из истории: `du ~/.[!.]*` даёт `zsh: event not found`. Вместо этого `du -h --max-depth=1 ~`.
- В блоке `cat <<'EOF'` кавычки вокруг `EOF` запрещают подстановки внутри.

### 20.5. Установка на телефон после пересборки

Из папки проекта: `adb install -r build/app/outputs/flutter-apk/app-release.apk`. Если `INSTALL_FAILED_UPDATE_INCOMPATIBLE`, то debug-ключи дома и на кампусе разные (Android защищает от подмены приложения): `adb uninstall com.vdarsuye.swifty_companion` и поставить заново. Проверка свежести: `adb shell dumpsys package com.vdarsuye.swifty_companion | grep lastUpdateTime`.

## 21. Android SDK «по частям» на новой машине кампуса (без Android Studio)

Этот раздел появился после второго подряд случая: на другой машине кампуса `goinfre` оказался пустым, и `flutter doctor` последовательно ругался на отсутствие SDK, потом на пустые `platforms`. Здесь собрано всё, чтобы в следующий раз пройти путь без вопросов.

### 21.1. Два способа получить SDK и чем они отличаются

| | С Android Studio | «По частям» (без IDE) |
|---|---|---|
| Кто качает компоненты | Окно **SDK Manager** одной галочкой | Ты сам командой `sdkmanager --install ...` |
| Кто принимает лицензии | Диалог при установке | `flutter doctor --android-licenses` |
| Кто вычисляет, что нужно | IDE ставит «рекомендованный набор» | Ты сам: Flutter не скажет, какая платформа ему нужна |
| Что может пойти не так | Занимает много места и памяти, на кампусе тормозит | Легко забыть компонент: `doctor` сообщает по одному |
| Когда выбирать | Если IDE нужна для работы | Если работаешь из терминала (наш случай) |

Android Studio по сути оболочка над теми же командами. Всё, что она делает галочками, можно сделать командами; разница только в том, что IDE за тебя собирает полный список, а «по частям» его надо знать.

### 21.2. Из чего состоит SDK и кому что нужно

| Папка в `~/goinfre/androidSDK` | Что это | Кому нужно | Что без неё |
|---|---|---|---|
| `cmdline-tools/latest/` | Менеджер пакетов (`sdkmanager`, `bin/`, `lib/`) | Нам, чтобы установить остальное и принять лицензии | `cmdline-tools component is missing`, `sdkmanager not found` |
| `platform-tools/` | `adb` (связь с телефоном) | Flutter: **по этой папке он признаёт каталог настоящим SDK** | `Unable to locate Android SDK`, хотя путь указан верно |
| `platforms/android-NN/` | Библиотеки Android нужной версии | Компилятору: `compileSdk` берётся из Flutter | `No valid Android SDK platforms found ... Directory was empty` |
| `build-tools/XX.Y.Z/` | Сборочные утилиты (упаковка APK) | Gradle при сборке | `doctor` и сборка ругаются на build-tools |
| `licenses/` | Файлы с хешами принятых лицензий | Gradle и `sdkmanager`: без них не качаются платформы | `Android license status unknown` |
| `ndk/` | Компилятор нативного кода | Gradle, при первой сборке докачивает сам | Долгая первая сборка (§12.2) |
| `emulator/`, `sources/` | Эмулятор, исходники Android | Нам **не нужны** (телефон по USB) | ничего |

Про «по этой папке Flutter признаёт SDK настоящим»: это вывод из наблюдения, а не цитата из кода Flutter. На практике, когда в SDK был только `cmdline-tools`, `doctor` писал `Unable to locate Android SDK`; после установки `platform-tools` эта строка пропала.

### 21.3. Полный чек-лист с нуля

Условия: Flutter уже склонирован (раздел 4), в `~/.zshrc` есть `PATH` для него, JDK 17 найден (раздел 7). Команды без комментариев в строке (раздел 15, первая строка).

**1. Скачать «Command line tools only» для Linux** со страницы https://developer.android.com/studio#command-line-tools-only и положить архив в `~/goinfre`.

**2. Разложить в нужную структуру** (должно получиться `cmdline-tools/latest/bin/sdkmanager`):

```bash
cd ~/goinfre
mkdir -p cmdtools_tmp androidSDK/cmdline-tools
unzip commandlinetools-linux-*_latest.zip -d cmdtools_tmp
mv cmdtools_tmp/cmdline-tools androidSDK/cmdline-tools/latest
ls androidSDK/cmdline-tools/latest/bin
```

**3. Поставить `platform-tools`:**

```bash
~/goinfre/androidSDK/cmdline-tools/latest/bin/sdkmanager --sdk_root=$HOME/goinfre/androidSDK --install "platform-tools"
```

`--sdk_root` задаёт корень SDK явно: так надёжнее, чем рассчитывать на то, что утилита сама поймёт, где она лежит. Кавычки вокруг имени пакета обязательны: `;` в именах пакетов оболочка читает как разделитель команд.

**4. Сказать Flutter, где SDK:**

```bash
flutter config --android-sdk "$HOME/goinfre/androidSDK"
```

**5. Принять лицензии** (на каждый вопрос `y`):

```bash
flutter doctor --android-licenses
```

**6. Узнать, какая платформа нужна этой версии Flutter, и поставить её с build-tools.** Номер платформы зависит от версии Flutter (`compileSdk = flutter.compileSdkVersion` в `android/app/build.gradle.kts`), поэтому его не угадывают, а читают из установленного Flutter:

```bash
grep -rn "compileSdkVersion" ~/goinfre/flutter/packages/flutter_tools/gradle/src/main/
~/goinfre/androidSDK/cmdline-tools/latest/bin/sdkmanager --sdk_root=$HOME/goinfre/androidSDK --list | grep "build-tools;" | tail -5
```

Первая команда показывает номер платформы `NN`, вторая список build-tools (выбирай самую свежую **без** `rc`, это не стабильная версия). Затем:

```bash
~/goinfre/androidSDK/cmdline-tools/latest/bin/sdkmanager --sdk_root=$HOME/goinfre/androidSDK --install "platforms;android-NN" "build-tools;XX.Y.Z"
```

**7. Проверить:** `flutter doctor`. Строка про Android toolchain должна быть зелёной. Красная строка про `ninja` и «Linux toolchain» не мешает (раздел 5).

**8. Вернуть то, что хранилось в `goinfre` и пропало вместе с ним** (раздел 21.5):

```bash
mkdir -p ~/goinfre/swifty_build
mkdir -p ~/goinfre/.gradle
```

и файл `~/goinfre/.gradle/gradle.properties` с лимитами памяти (раздел 20.1).

**9. Проверка цепочки:** `echo $GRADLE_USER_HOME`, `which adb` и `adb devices` (телефон по кабелю), затем `flutter pub get && flutter analyze && flutter test`. Первая сборка будет долгой: докачивается NDK и всё остальное (§12.2).

### 21.4. Таблица: что говорит `flutter doctor` и чего не хватает

| Сообщение | Чего не хватает | Что делать |
|---|---|---|
| `Unable to locate Android SDK` | Папки `platform-tools` (или неверный путь) | Шаги 3–4; проверить `ls ~/goinfre/androidSDK` |
| `cmdline-tools component is missing` / `sdkmanager not found` | `cmdline-tools/latest` | Шаги 1–2 |
| `Android license status unknown` | Принятых лицензий | Шаг 5 |
| `No valid Android SDK platforms found in .../platforms. Directory was empty` | Ни одной платформы | Шаг 6 |
| сообщение про `build-tools` | Папки `build-tools` | Шаг 6 (точный текст сообщения я не видела, поэтому не привожу) |
| `adb: command not found` | `platform-tools` нет в `PATH` | Раздел 9.3 |

Сообщения идут **по одному**: поставил один компонент, и `doctor` показывает следующий. Это не значит, что ты что-то сделал не так.

### 21.5. Что пропадает на новой машине, а что остаётся

`goinfre` свой у каждой машины и периодически чистится. Домашняя папка общая, поэтому там остаётся то, что в ней лежит. Отсюда ловушка: в общем проекте остаются ссылки на то, чего на новой машине нет.

| Что | Где лежит | На новой машине |
|---|---|---|
| Исходники, `.git`, `~/.zshrc` (`PATH`, `GRADLE_USER_HOME`) | домашняя папка | на месте |
| Ссылка `build -> ~/goinfre/swifty_build` в проекте | домашняя папка | на месте, но **висит в воздухе**: цели нет. Лечится `mkdir -p ~/goinfre/swifty_build` |
| Flutter SDK | `~/goinfre/flutter` | **нет**, клонировать заново (раздел 4); версия может оказаться новее (мы видели 3.47 на одной машине и 3.50 на другой) |
| Android SDK | `~/goinfre/androidSDK` | **нет**, чек-лист 21.3 |
| Кэш Gradle и **лимиты памяти** (`gradle.properties`) | `~/goinfre/.gradle` | **нет**; без файла Gradle берёт шаблонные 8 ГБ и машина может повиснуть |
| Конфиг IDE | `~/goinfre/android-studio-config` | нет, если IDE нужна |

Мини-проверка после чистого `goinfre`: `ls ~/goinfre` должно показать `flutter`, `androidSDK`, `swifty_build`, а `ls -a ~/goinfre` ещё и `.gradle`.

### 21.6. Подводные камни

- **Номер платформы зависит от версии Flutter.** Не копируй `android-36` из чужой инструкции: прочти номер из установленного Flutter (шаг 6).
- **Разные версии Flutter на разных машинах.** После наладки SDK запусти `flutter analyze` и `flutter test` и убедись, что поведение не изменилось. Закрепить версию можно способом из раздела 17.4.
- **Кавычки.** Имена пакетов с `;` берут в кавычки; пути с `~` внутри кавычек не раскрываются, поэтому пиши `$HOME`.
- **JDK обязателен для `sdkmanager`** (раздел 7). Без Java утилита не запустится.
- **Не прерывай первую сборку** (NDK распаковывается долго, раздел 12.2).
- **Комментарии `#` в строке команды в zsh не комментарии** (раздел 15).
- **Предупреждение про устаревший `sdkmanager`** информационное (раздел 6.5).

### 21.7. Альтернативы

| Вариант | Плюсы | Минусы |
|---|---|---|
| Android Studio и её SDK Manager | Меньше знать наизусть | Тяжёлая, на кампусе тормозит; лишний слой |
| Как в этом разделе, по частям | Лёгкий, понятный, повторяемый | Надо знать список компонентов |

| Работать дома, на кампусе только `analyze` и `test` | Никакой возни с SDK | Для демонстрации APK нужен дом или заранее собранный файл |
