# Flutter и React Native: в чём разница, плюсы и минусы обоих

Вопрос «почему Flutter, а не React Native?» почти гарантированно прозвучит на защите. Хорошая новость: честный ответ у нас есть, и он не сводится к «потому что в задании написано Flutter». Плохая: в интернете про эту пару пишут много маркетинга, и половина цифр там устарела. Поэтому здесь каждое утверждение либо проверено по официальным источникам, либо помечено как оценка.

Дата актуальности: **18 октября 2026**. Оба фреймворка быстро меняются, и через полгода часть деталей устареет. Номера версий ниже нужны не для запоминания, а чтобы ты понимал, насколько всё подвижно.

---

## 1. Суть в одном абзаце

Оба решают одну задачу: **один код на несколько платформ**. Но подходят к ней противоположно.

- **Flutter** (Google, язык Dart) **рисует интерфейс сам**: свой графический движок отрисовывает каждый пиксель. Операционная система даёт ему только окно и события касания.
- **React Native** (Meta, язык JavaScript/TypeScript) **управляет настоящими нативными элементами**: JavaScript говорит платформе «покажи кнопку, вот её параметры», а кнопку рисует Android или iOS.

Всё остальное (производительность, внешний вид, экосистема, найм) вытекает из этого одного различия. Если запомнить только одно: **Flutter приносит с собой свой «рисовальщик», React Native использует чужой, системный**.

## 2. Устройство изнутри

### 2.1 Flutter

| Слой | Что делает |
|---|---|
| Фреймворк на Dart | Виджеты, раскладка, анимации, жесты. Всё написано на Dart, в том числе кнопки и списки |
| Движок на C++ | Отрисовка (Impeller), текст, работа с платформой |
| Встраиватель (embedder) | Тонкая платформенная прослойка: окно, ввод, каналы к нативному коду |

Dart работает в двух режимах:

- **Разработка (debug)**: JIT-компиляция в виртуальной машине. Отсюда **hot reload**: изменённый код подгружается в работающее приложение за секунду, состояние сохраняется.
- **Релиз**: AOT-компиляция в машинный код. Нет интерпретатора и нет «моста»: Dart-код исполняется как обычная нативная программа.

**Impeller** это текущий движок отрисовки. По документации Flutter, он используется по умолчанию на Android с API 29 и выше (на более старых устройствах запасной путь через OpenGL), на iOS он единственный, а на десктопе стал вариантом по умолчанию в версии 3.47. Веб всё ещё использует другой путь (Skia/CanvasKit). Его главная идея: **заранее скомпилированные шейдеры**. Старый движок Skia компилировал шейдеры в момент первой отрисовки эффекта, из-за чего случались рывки при первом показе анимации («шейдерный джанк»). Impeller устраняет это класс проблем: всё готово заранее.

### 2.2 React Native

| Слой | Что делает |
|---|---|
| JavaScript/TypeScript + React | Твой код: компоненты, состояние, логика |
| Движок JS (Hermes) | Исполняет JavaScript. Hermes компилирует код в байткод заранее, что ускоряет запуск |
| JSI | Прямая связь между JS и C++ без сериализации в JSON. Заменила старый асинхронный «мост» |
| Fabric | Новый рендерер: превращает дерево React в дерево нативных видов (`View`, `TextView` и т. д.) |
| TurboModules | Новый способ вызова нативных модулей (камера, файлы): по требованию и без сериализации |

Исторический контекст, важный для понимания критики. Старый React Native (до «новой архитектуры») общался с нативным кодом через **асинхронный мост**, где всё превращалось в JSON-сообщения. Отсюда ходячие обвинения «RN тормозит, мост узкое место». **Новая архитектура** (JSI, Fabric, TurboModules) эту проблему убрала. По блогу React Native: в версии 0.82 (октябрь 2025) архитектура стала полностью новой (старая заморожена начиная с 0.80), в 0.84 по умолчанию включён Hermes V1 и удалены старые компоненты. Версия 0.87 вышла в августе 2026 (строгий TypeScript API, обновление Metro, AGP 9, Node 22). Поэтому критику «мост тормозит» нужно читать с оговоркой: в современных версиях это уже не так, а вот в старых туториалах и старых проектах да.

### 2.3 Картинка для запоминания

```text
Flutter:                                  React Native:

  Твой код (Dart)                           Твой код (JS/TS + React)
        │                                         │
  Виджеты Flutter                            Hermes (JS-движок)
        │                                         │
  Свой движок (Impeller)                      JSI / Fabric
        │                                         │
  Холст окна (GPU)                         Нативные View Android/iOS
                                                  │
                                              Экран (GPU)
```

В Flutter между твоим кодом и пикселями нет нативных элементов ОС. В React Native они есть, и это одновременно главное достоинство (родной вид) и главная головная боль (расхождения между платформами).

## 3. Сравнение по темам

### 3.1 Язык

| | Flutter: Dart | React Native: JavaScript / TypeScript |
|---|---|---|
| Типизация | Статическая, строгая, null safety встроена | JS динамический; TypeScript добавляет типы поверх (0.87 ужесточает типизацию API) |
| Порог входа | Нужно учить новый язык, но он похож на Java/C#/C++; тебе, после C/C++ и Java, зайдёт легко | Если знаешь веб, порог низкий. Но JS/TS со своей экосистемой (npm, Node) сам по себе большой |
| Где ещё полезен язык | Практически только Flutter и немного серверный Dart | JavaScript везде: веб, сервер, десктоп. Это огромный плюс |
| Ошибки | Многое ловится при компиляции | В чистом JS много ошибок всплывает только в рантайме; TS это частично лечит |

Вывод: **у React Native выигрыш по «ценности языка за пределами фреймворка»**. Выучив JS/TS, ты можешь писать на нём что угодно. Dart за пределами Flutter почти не нужен. У Dart выигрыш в строгости и предсказуемости.

### 3.2 Внешний вид интерфейса

| | Flutter | React Native |
|---|---|---|
| Подход | Рисует сам, поэтому выглядит **одинаково** везде | Использует нативные элементы, поэтому выглядит **как родное** на каждой платформе |
| Плюс | Полный контроль над пикселями (наш стимпанк с шестерёнками, потёртостями и градиентами это сильная сторона Flutter, см. [docs/12](12-steampunk-design.md)) | Приложение автоматически получает новое оформление ОС после её обновления |
| Минус | Нативные элементы **имитируются**. После обновления ОС возможны мелкие расхождения; надо дорабатывать самим | Одно и то же может выглядеть и вести себя чуть по-разному на Android и iOS; кастомная графика сложнее |

Для нашего проекта это решающий довод в пользу Flutter: рисование на `Canvas` (`CustomPainter`) с произвольными путями, размытием и обрезкой это штатная возможность, а в React Native пришлось бы подключать сторонние библиотеки (обычно `react-native-svg` или Skia-обёртку).

### 3.3 Производительность

Честная картина без рекламы:

| Критерий | Flutter | React Native |
|---|---|---|
| Исполнение кода | AOT, машинный код | JS через Hermes (байткод), вызовы в нативный код через JSI |
| Анимации и сложная графика | Сильная сторона: свой движок, 60/120 кадров в секунду, предсказуемо | Хорошо для обычного интерфейса; для тяжёлой графики часто нужны нативные модули или специальные библиотеки |
| Запуск | Движок Flutter стартует вместе с приложением | Нужно поднять JS-движок и загрузить бандл; Hermes это сильно ускорил |
| Обычные экраны со списками и формами | Разница для пользователя на практике почти незаметна | То же |

Оговорка, которую нужно сказать честно: **большинство «бенчмарков» в интернете сделано вендорами или блогерами** и сравнивает не равные условия. Устойчивого независимого вывода «X быстрее Y в целом» я не нашла. Для приложения вроде нашего (два экрана и пара запросов) обе технологии работают с огромным запасом, и производительность не должна быть аргументом ни за одну из них.

### 3.4 Скорость разработки и инструменты

| | Flutter | React Native |
|---|---|---|
| Hot reload | Очень быстрый и надёжный, сохраняет состояние | Fast Refresh, тоже быстрый; иногда требует полного перезапуска |
| Комплектность | «Всё в коробке»: навигация, анимации, тема, тесты, инструменты (Widget Previews стали стабильными в 3.47) | Минимальное ядро; навигацию, состояние и многое другое берут из экосистемы (React Navigation и т. д.) |
| Диагностика | `flutter doctor` проверяет окружение; DevTools | Metro, Flipper/DevTools; цепочка Node + Gradle + Xcode бывает капризной |
| Быстрый старт | Нужен Flutter SDK и Android SDK | **Expo** позволяет начать почти без настройки окружения, это сильный плюс RN для новичков |
| Обновления | Несколько релизов в год; изменения бывают крупными (в 3.47 виджеты Material и Cupertino вынесены в отдельные пакеты `material_ui` и `cupertino_ui` версии 1.0, как необязательный вариант) | Версии выходят часто, миграции между ними известны своей болезненностью (хотя новая архитектура это улучшила) |

Про вынесение Material из ядра Flutter: идея в том, что ядро фреймворка перестаёт зависеть от конкретного дизайн-языка, и виджеты Material развиваются независимо. Для нас практически ничего не меняется, но это хороший пример «скорости изменений», о которой мы говорили в [README, раздел 4.6](../README.md#46-минусы-flutter-и-риски-о-них-лучше-сказать-самим).

### 3.5 Экосистема и библиотеки

| | Flutter | React Native |
|---|---|---|
| Репозиторий пакетов | pub.dev | npm |
| Размер | Большой и растущий; многие пакеты поддерживаются Google или сообществом | **Огромный**: весь npm, плюс специализированные библиотеки для RN |
| Качество | Пакеты обычно единообразны и подчиняются правилам pub.dev | Очень разное: от отличных до заброшенных; бывает, что библиотека не поддерживает вашу версию RN |
| Нативные возможности | Через плагины и platform channels; при отсутствии нужного плагина надо писать Kotlin/Swift | Через нативные модули; то же самое |
| Использование веб-кода | Нет, веб-библиотеки JS не подключить напрямую | Часть чистой JS-логики (валидаторы, форматирование дат) можно переиспользовать |

### 3.6 Платформы

| | Flutter | React Native |
|---|---|---|
| Android, iOS | Да | Да |
| Веб | Да (рисует на холсте; подходит для приложений, хуже для контентных сайтов; поддержка WebAssembly развивается) | Через дополнительные решения (React Native for Web, Expo) |
| Десктоп | Windows, macOS, Linux (в 3.47 Impeller по умолчанию на десктопе) | Windows и macOS через проекты Microsoft; Linux неофициально |
| Встроенные системы | Есть примеры | Редко |

В официальной поддержке платформ Flutter шире «из коробки». У React Native сильнее связь с вебом (сам React).

### 3.7 Размер приложения

Flutter-приложение включает свой движок, поэтому «пустое» приложение больше нативного (порядок нескольких мегабайт сверху). React Native включает JS-движок и код бандла, и «пустое» приложение тоже больше нативного. Разница между ними не принципиальна, а точные цифры сильно зависят от версии и настроек сборки, поэтому конкретных мегабайт я здесь не называю. Для нашего проекта размер не критичен.

### 3.8 Тестирование

Оба имеют хорошую поддержку тестов. В нашем проекте 223 теста на Flutter: юнит-тесты (`MockClient`), тесты виджетов (`testWidgets`), быстрые, без телефона. Для React Native обычно используют Jest и React Native Testing Library. Принципиально разницы нет; у Flutter тестовая среда входит в SDK.

### 3.9 Рынок, популярность, найм

Цифры собраны из разных источников и **измеряют разные вещи**. Не складывай их в одну картину слишком уверенно.

| Показатель | Flutter | React Native | Источник и оговорка |
|---|---|---|---|
| Опрос Stack Overflow 2024: доля использующих | 9,4 % | 8,4 % | Доли от всех респондентов; разрыв небольшой |
| Опрос Stack Overflow 2024: среди профессионалов | 9,4 % | 9,0 % | Почти поровну |
| Опрос Stack Overflow 2024: среди учащихся | 11,1 % | 6,7 % | Flutter популярнее среди тех, кто учится |
| Опрос Stack Overflow 2024: «любимый» (admired) | 60,6 % | 56,5 % | Доля тех, кто пользовался и хочет продолжать |
| Опрос Stack Overflow 2025 | нет сопоставимых данных | нет сопоставимых данных | В ранее найденных пересказах блогов цифры 9,12 % и 8,43 %; я не смогла подтвердить их первоисточником, поэтому не опираюсь |
| Звёзды на GitHub (июль 2026) | около 177,9 тыс. | около 126,2 тыс. | Звёзды измеряют интерес, а не использование |
| Авторы кода за всё время | около 2 363 | около 4 227 | У RN больше участвовавших разработчиков (в том числе из-за истории проекта) |
| Топ-10 000 приложений iOS (кроме игр), декабрь 2025 | 1 184 приложения, около 38 % загрузок, 32 % выручки | 1 350 приложений, около 47 % загрузок, 41 % выручки | Appfigures; только iOS, только крупные приложения |
| Приложения с доходом больше 1 млн $ в месяц (октябрь 2024) | 37 | 173 | Внимание: данные на 2024 год, и по ним React Native сильнее в коммерческом секторе |
| Количество вакансий | нет надёжных данных | нет надёжных данных | В блогах чаще пишут, что вакансий по RN больше (его проще найти у компаний с веб-командами на React), но убедительного источника с цифрами я не нашла. **Проверь сам** на InfoJobs, LinkedIn, Indeed по Барселоне |

Общий вывод по рынку (мой, с оговорками):

- Популярность по опросам у них **сопоставима**, и Flutter немного впереди у начинающих.
- В **коммерческом секторе** и в крупных приложениях по доступным данным заметнее React Native (особенно в США и у компаний, у которых уже есть веб-разработчики на React).
- Для **найма** это значит: если ты хочешь максимум вакансий, JS/TS и React это более широкий вход (веб, сервер и мобильные), а Flutter более узкая, но живая ниша.

Известные примеры: на React Native сделаны части приложений Meta (Facebook, Instagram — частично), Shopify, Discord (мобильное приложение), Microsoft Office-части; Flutter используют, например, Google Pay, BMW (приложение My BMW), Alibaba (Xianyu), eBay Motors. Это общеизвестные примеры из публичных кейсов; точный перечень со временем меняется, поэтому на защите лучше говорить «например» и не клясться в деталях.

### 3.10 Управление проектом и риски

| | Flutter | React Native |
|---|---|---|
| Кто стоит за проектом | Google. Код открыт (BSD), но развитием управляет Google. Есть форк Flock (октябрь 2024, из-за недовольства вложениями Google) | Meta, плюс крупный экосистемный вклад Microsoft, Expo, Callstack и других. Код открыт (MIT) |
| Главный риск | Решения Google (она закрывала проекты и раньше); Dart почти нигде больше не нужен | Хрупкость сборки: зависимости, нативные модули и версии могут конфликтовать; миграции между версиями |
| Устойчивость | Сильная вовлечённость Google, активное сообщество | Крупнейшее сообщество JS, но зависимость от нескольких вендоров |

## 4. Итоговая таблица плюсов и минусов

### Flutter

| Плюсы | Минусы |
|---|---|
| Один рендерер: интерфейс идентичен на всех платформах и версиях ОС | Нативные элементы имитируются: возможны мелкие расхождения после обновлений ОС |
| Сильная графика и анимации (`Canvas`, `CustomPainter`, Impeller без шейдерных рывков) | Приложение тяжелее чисто нативного (в нём едет движок) |
| Release компилируется в машинный код; нет JS-моста | Нужен Dart, который почти нигде кроме Flutter не нужен |
| Hot reload сохраняет состояние | Нативные возможности без готового плагина приходится писать на Kotlin/Swift |
| «Всё в коробке»: тесты, тема, навигация, инструменты | Веб-версия не подходит для контентных сайтов и слабее по SEO |
| Единообразная экосистема pub.dev | Меньше вакансий и более узкий рынок, чем у JS-стека (по общим оценкам) |
| Статическая типизация и null safety из коробки | Частые крупные изменения (например, вынос Material); старые туториалы устаревают |
| Широкая поддержка платформ (мобильные, веб, десктоп) | Зависимость от одного вендора (Google) |

### React Native

| Плюсы | Минусы |
|---|---|
| Нативные элементы: родной вид и поведение на каждой платформе | Расхождения между Android и iOS, нужно проверять обе |
| JS/TS и React: огромный пул разработчиков, полезно далеко за пределами мобильной разработки | Хрупкая цепочка сборки (Node, Metro, Gradle, Xcode) и конфликты версий зависимостей |
| Огромная экосистема npm | Качество библиотек очень разное; бывают заброшенные |
| Expo: быстрый старт без сложной настройки | Кастомная графика и сложные анимации сложнее, чем во Flutter |
| Больше крупных коммерческих приложений по доступным данным | Много решений нужно принимать самому (навигация, состояние), единого стиля меньше |
| Можно переиспользовать веб-знания и часть веб-кода | Миграции между версиями исторически болезненны (хотя новая архитектура ситуацию улучшила) |
| Новая архитектура (JSI, Fabric, TurboModules, Hermes) убрала старый мост | Динамическая типизация JS (TypeScript смягчает, но не отменяет) |

## 5. Когда что выбирать

| Ситуация | Что разумнее | Почему |
|---|---|---|
| Команда веб-разработчиков на React | React Native | Те же навыки, тот же язык, часть кода общая |
| Продукт с яркой, нестандартной графикой и анимациями | Flutter | Свой рендерер даёт полный контроль |
| Нужен интерфейс, неотличимый от системного, на обеих платформах | React Native (или полностью нативный код) | Использует настоящие элементы ОС |
| Прототип за выходные, мало знаний об окружении | React Native с Expo | Минимум настройки |
| Одинаковый внешний вид на мобильных, вебе и десктопе | Flutter | Один код, один вид |
| Хочется строгости и предсказуемости языка | Flutter | Dart статический, с null safety |
| Максимум вакансий и гибкость карьеры | JS/TS-стек (в том числе React Native) | Язык применим везде |
| Приложение со сложной нативной интеграцией (камера, Bluetooth, специфичный SDK) | Нативная разработка или любой из двух с готовым плагином | Всё зависит от наличия поддержки в экосистеме |
| Нужна только Android-разработка максимального качества | Kotlin + Jetpack Compose | Родной стек Google для Android |

Нет универсально лучшего. Выбор определяют **команда, продукт и сроки**.

## 6. Как это применимо к нашему проекту

Swifty Companion это два экрана, один HTTP-клиент, OAuth2 и яркая отрисовка. Что из этого значит:

1. **Оба фреймворка справились бы.** Приложение простое. Производительность не должна быть аргументом ни за одно решение.
2. **В задании назван Flutter.** Это решающий и совершенно законный довод: задание школы мобильной инициации ориентировано на Flutter (и вообще современные кроссплатформенные инструменты).
3. **Новый навык.** Ты уже делал Android-проект (ft_hangouts, нативный Android). Flutter даёт другую парадигму: декларативные виджеты и свой рендерер.
4. **Стимпанк-оформление.** Наши шестерёнки, потёртости, клёпки и размытые пятна окиси сделаны через `CustomPainter`, `Path`, `MaskFilter` и `ShaderMask`. Это сильная сторона Flutter.
5. **Среда Linux в кампусе.** Flutter + Android SDK + Gradle на Linux работают. iOS недоступна (нужен macOS), и для этого ни Flutter, ни React Native не помогут: любая iOS-сборка требует Xcode.
6. **Минимум зависимостей.** Нам хватило `http` и `flutter_dotenv`. В React Native мы бы тоже обошлись `fetch` и небольшой библиотекой для конфигурации, но пришлось бы настраивать связку Node + Metro + Gradle.

Что бы я выбрала для **другого** проекта, в котором ты захочешь быстрее выйти на рынок труда как веб-разработчик: React Native, если ты планируешь сочетать мобильную разработку с вебом. А если тебе интереснее мобильная разработка с красивой графикой и строгим языком: Flutter. Честный ответ на защиту: «Я выбрал Flutter из-за задания и из-за графики; для команды веб-разработчиков на React я бы выбрал React Native».

## 7. Вопросы для защиты по этой теме

| Вопрос | Ответ |
|---|---|
| Чем Flutter принципиально отличается от React Native? | Flutter рисует интерфейс сам (движок Impeller, Dart компилируется в машинный код). React Native управляет настоящими нативными элементами платформы из JavaScript |
| Что такое мост в React Native и почему о нём говорят? | В старой архитектуре JS и нативный код общались асинхронными JSON-сообщениями, и это было узким местом. Новая архитектура (JSI, Fabric, TurboModules) от моста отказалась; начиная с 0.82 она единственная |
| Что такое hot reload и как он работает? | В debug Dart выполняется в виртуальной машине с JIT; новый код подгружается в уже работающий процесс, а состояние виджетов сохраняется |
| Что такое Impeller и зачем он нужен? | Движок отрисовки Flutter. Шейдеры компилируются заранее, поэтому нет рывков при первом показе эффекта |
| Минусы Flutter? | Больший размер приложения, имитация нативных элементов, Dart нужен почти только для Flutter, зависимость от Google, частые изменения |
| Минусы React Native? | Расхождения между платформами, хрупкая цепочка зависимостей, качество библиотек различается, сложнее с кастомной графикой |
| Почему не React Native? | В задании Flutter; для нашей кастомной графики Flutter удобнее; хотелось нового навыка. Для команды веб-разработчиков RN был бы разумнее |
| Кто больше используется? | По опросам сопоставимо, у учащихся Flutter впереди; в крупных коммерческих приложениях по данным 2024–2025 года заметнее React Native. Точных цифр по вакансиям я не утверждаю |
| Можно ли подключить веб-библиотеку на JS во Flutter? | Нет, напрямую нельзя; нужен пакет Dart или канал к нативному коду |

## 8. Ловушки и чего избегать в разговоре

- **Не повторять «Flutter быстрее» или «React Native тормозит»** без оговорок. Это старые лозунги: первое зависит от задачи, второе относится к старой архитектуре.
- **Не называть устаревшие цифры «актуальными».** Например, «46 % против 35 %» это опрос Statista 2023 года.
- **Не доверять вендорским статьям.** В одной из просмотренных (статья компании Infomaze) перепутаны версии, в которых Impeller и новая архитектура стали основными. Проверять по официальным страницам: блог React Native, документация Flutter по Impeller и заметки к релизу Flutter 3.47.
- **Не обещать, что один код на «все платформы» работает без доработок.** В обоих случаях платформенные тонкости (разрешения, уведомления, фоновая работа, сборка под iOS) требуют отдельной работы.
- **Не забывать, что оба фреймворка не умеют собирать iOS без macOS.**
