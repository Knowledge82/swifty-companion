## 2. Теория: что такое разбор JSON и где он ломается

### 2.1 Что приходит из сети

Сервер присылает **текст**:

```text
{"login":"jdoe","phone":"hidden","wallet":42,"cursus_users":[{"level":12.44, ...}]}
```

Функция `jsonDecode` из `dart:convert` превращает его в обычные Dart-структуры:

| В JSON | В Dart после `jsonDecode` |
|---|---|
| объект `{...}` | `Map<String, dynamic>` |
| массив `[...]` | `List<dynamic>` |
| строка | `String` |
| число | `int` **или** `double` |
| `true` / `false` | `bool` |
| `null` | `null` |

Тип `dynamic` значит «компилятор не знает, что внутри». Проверка откладывается до момента выполнения.

### 2.2 Где ломается наивный разбор

Самый простой способ:

```dart
final login = json['login'] as String;
final level = json['level'] as double;
```

Что может пойти не так на **реальных данных 42** (всё это мы уже видели в [docs/03](03-api-exploration.md)):

| Ситуация | Что произойдёт при наивном `as` |
|---|---|
| Поле отсутствует или `null` (например, `final_mark` у одного проекта) | `TypeError`, приложение падает |
| Уровень пришёл как `7`, а не `7.0` | `json['level'] as double` падает: `int` не `double` |
| `phone` пришёл строкой `"hidden"` | не падает, но на экран попадёт слово hidden как будто это телефон |
| `3.4699999999999998` | не падает, но на экране уродливое число |
| В списке проектов оказался элемент не того типа | падение на всём списке |
| Ключ называется `validated?` (с вопросом) | легко опечататься, получить `null` и не заметить |

Задание требует: **обрабатывать все ошибки и не показывать скрытое**. Значит, разбор должен быть **терпимым** (tolerant): неожиданное превращается в «нет данных», а не в аварию.

### 2.3 Два вида разбора

| | Строгий (strict) | Терпимый (tolerant) |
|---|---|---|
| Идея | любое отклонение от схемы это ошибка | отклонение превращается в «пусто» |
| Плюс | сразу видно, что API изменился | приложение продолжает работать |
| Минус | одно кривое поле роняет всё | можно не заметить, что данные не пришли |
| Где уместно | обязательные данные, без которых смысла нет | необязательные данные для показа |

Мы **комбинируем**: `login` обязателен (нет логина, нет профиля, бросаем `FormatException`), всё остальное терпимо. Репозиторий (этап 4) превратит `FormatException` в понятную пользователю ошибку «неожиданный ответ сервера».

### 2.4 Зачем отдельные классы-модели

Можно было бы везде таскать `Map<String, dynamic>` и дёргать `json['cursus_users'][1]['level']`. Но:

- опечатка в ключе обнаруживается только при запуске, и то как `null`;
- логика («какой курс основной», «какие проекты завершены») размазалась бы по экранам;
- экраны пришлось бы тестировать, подсовывая гигантские JSON.

Модель собирает правила **в одном месте**: экран получает `profile.mainCursus`, `profile.finishedProjects()`, `profile.phone.orNA` и ничего не знает про `"hidden"` и `validated?`. Это же упрощает защиту: «вот правила, вот тесты на них».

Принцип называется **«parse, don't validate»**: разобрать входные данные один раз на границе системы в строгие типы, а дальше работать только с ними.

## 3. Карта: поле JSON → поле модели → что при пустоте

| Источник в JSON | Поле модели | Правило при `null` / отсутствии / `"hidden"` |
|---|---|---|
| `login` | `UserProfile.login` | **обязательно**, иначе `FormatException` |
| `id` | `UserProfile.id` | `null` |
| `displayname` | `displayName` | `null` → на экране N/A |
| `email`, `phone`, `location` | то же имя | `null` (в том числе из `"hidden"`) → N/A |
| `wallet` | `wallet` | `null` |
| `correction_point` (единственное число) | `correctionPoints` | `null` |
| `pool_month`, `pool_year` | `poolMonth`, `poolYear` | `null` |
| `image.versions.medium` → `image.link` → `large` → `small` → `micro` | `imageUrl` | первый подходящий https-адрес, иначе `null` (экран покажет заглушку) |
| `cursus_users[]` | `cursuses` | пустой список |
| `cursus_users[].cursus_id` (иначе `cursus.id`) | `CursusProgress.cursusId` | `null` |
| `cursus_users[].cursus.name` / `.slug` | `name`, `slug` | `null` |
| `cursus_users[].level` | `level` | `0`, округляется до 2 знаков |
| `cursus_users[].begin_at` / `end_at` | `beginAt`, `endAt` | `null` |
| `cursus_users[].skills[]` | `skills` | пустой список |
| `skills[].id` | `Skill.id` | `null` |
| `skills[].name` | `Skill.name` | «Без названия» |
| `skills[].level` | `Skill.level` | `0`, округляется до 2 знаков |
| `projects_users[]` | `projects` | пустой список; элементы не-объекты пропускаются |
| `projects_users[].project.name` → `project.slug` | `ProjectResult.name` | название, иначе slug, иначе «Без названия» |
| `projects_users[].status` | `status` | `null`; `isFinished` это `status == 'finished'` |
| `projects_users[].validated?` | `validated` | `null` значит `ProjectOutcome.unknown` |
| `projects_users[].final_mark` | `finalMark` | `null` → N/A |
| `marked_at` → `updated_at` → `created_at` | `date` | первая валидная дата, иначе `null` |
| `projects_users[].cursus_ids[]` | `cursusIds` | пустой список |

**Чего в модели нет сознательно:** `anonymize_date`, `data_erasure_date`, `alumnized_at`, `achievements`, `expertises_users`, `campus_users` и прочего. Правило: **разбираем только то, что показываем**. Меньше кода, меньше шансов случайно вывести лишнее, и не нужно поддерживать то, чего никто не видит. Это же закрывает пункт задания про приватность.

## 4. Функции безопасного чтения

Все в `lib/core/json_reader.dart`. Общий принцип: **неподходящий тип даёт `null` (или пустой список), а не исключение**.

| Функция | Принимает | Возвращает | Примеры |
|---|---|---|---|
| `readString` | `String`, `int` | `String?` (обрезанная) | `'  a '` → `'a'`; `''`, `'   '`, `'hidden'`, `'HIDDEN'`, `null`, `true` → `null`; `2023` → `'2023'` |
| `readDouble` | `int`, `double` | `double?` | `7` → `7.0`; `'9.6'` → `null`; `NaN`, `∞` → `null` |
| `readInt` | `int`, `double` | `int?` | `5` → `5`; `4.6` → `5`; `'5'` → `null` |
| `readBool` | `bool` | `bool?` | `true` → `true`; `'true'` → `null` |
| `readMap` | любая `Map` | `Map<String, dynamic>?` | не-объект → `null` |
| `readList` | `List` | `List<Object?>` | не-список → пустой |
| `readDate` | ISO 8601 текст | `DateTime?` | `'2024-03-01T10:00:00.000Z'` → дата; `'вчера'` → `null` |
| `readObjects<T>` | список объектов + функция разбора | `List<T>` | элементы, которые не объекты, пропускаются |

### 4.1 Симуляция: `readString` на реальных значениях

| Вход | Шаг 1: `int`? | Шаг 2: `String`? | Шаг 3: обрезка | Шаг 4: пусто или hidden? | Итог |
|---|---|---|---|---|---|
| `'Jane'` | нет | да | `'Jane'` | нет | `'Jane'` |
| `'hidden'` | нет | да | `'hidden'` | **да** | `null` |
| `' Hidden '` | нет | да | `'Hidden'` | **да** (сравнение в нижнем регистре) | `null` |
| `''` | нет | да | `''` | **да** | `null` |
| `null` | нет | нет | | | `null` |
| `2023` | **да** | | | | `'2023'` |
| `true` | нет | нет | | | `null` |

### 4.2 Почему `readString` принимает `int`

На случай, если API вдруг отдаст год числом (`2023` вместо `"2023"`). Поле всё равно показываем как текст. Это мелкая страховка, дорогой она не стоит.

### 4.3 `readObjects`: один элемент не роняет список

```dart
readObjects(json['projects_users'], ProjectResult.fromJson)
```

Для каждого элемента списка проверяется, что это объект. Если нет, элемент молча пропускается. Так из 6 элементов (один «мусорный») получится 5 проектов, как в тесте.

Это компромисс: можно было бы падать. Но «потеряли одну запись» лучше, чем «не показали ничего».

## 5. Принятые решения, по одному

### 5.1 `"hidden"` превращаем в `null` **в модели**, а не на экране

Проверка в одном месте (`readString`), экраны пишут просто `profile.phone.orNA`.

| Вариант | Плюсы | Минусы |
|---|---|---|
| **В модели (выбрано)** | единое правило; экран не может «забыть»; гарантия приватности проверяется тестом | теряем различие «скрыто» и «нет данных» (для нас оба N/A) |
| На экране | сохраняется исходное значение | каждый экран должен помнить про `"hidden"`, легко забыть в одном месте |
| Хранить в модели enum «значение / скрыто / нет» | сохраняет всю информацию | усложнение без пользы: показываем всё равно N/A |

Если когда-нибудь захочется различать («скрыто пользователем» против «не указано»), перейти на enum можно локально, в `readString`.

### 5.2 Расширение `orNA`

```dart
profile.phone.orNA        // 'N/A' или телефон
profile.wallet.orNA       // 'N/A' или '42'
```

Расширение (`extension`) добавляет метод к существующему типу без наследования. Здесь оно на `Object?`, поэтому работает и для `String?`, и для `int?`. Цена: появляется «метод у всего подряд». Для маленького проекта это нормально, но если захочется строгости, можно сделать отдельные расширения для `String?` и `int?`.

### 5.3 Логин обязателен

`UserProfile.fromJson` бросает `FormatException`, если `login` отсутствует, пуст или равен `"hidden"`. Ответ без логина не профиль, а признак того, что API вернул что-то не то.

### 5.4 Выбор основного курса

Алгоритм `pickMainCursus`:

1. Список пуст → `null`.
2. Есть курс со `slug == '42cursus'` → он.
3. Иначе курс с наибольшим `level`.

Симуляция на данных фикстуры (порядок нарочно «неудобный»):

| # | slug | level | Что делает алгоритм |
|---|---|---|---|
| 1 | `c-piscine` | 5.02 | slug не совпал, идём дальше |
| 2 | `42cursus` | 3.0 | **совпал**, возвращаем (хотя уровень ниже, чем у первого) |
| 3 | `c-piscine-reloaded` | 0.0 | не рассматривается |

Если бы `42cursus` не было (студент с одним бассейном), шаг 3 вернул бы курс с максимальным уровнем через `reduce`.

**Почему не «первый в списке» и не «самый высокий уровень сразу».** Первый в списке это случайность порядка ответа API. Самый высокий уровень неверен для студентов, у которых бассейн (около 5) выше только что начатого основного курса.

**Риск:** `slug == '42cursus'` взят из реального ответа, но есть ли такой курс у всех студентов и не меняется ли он, мы проверили только на одном профиле.

### 5.5 Что такое «завершённый проект»

`isFinished` это строго `status == 'finished'`. **Сдан/провален** определяет `outcome` по `validated?`:

| `validated?` | `outcome` |
|---|---|
| `true` | `passed` |
| `false` | `failed` |
| `null` / нет | `unknown` |

Почему не по `validated?` вместо статуса: в реальных данных 41 запись с `validated? == true` при 40 завершённых, то есть есть как минимум один не завершённый проект с «сдан». Фикстура воспроизводит этот случай (`minishell`, статус `in_progress`, `validated?: true`), и тест следит, чтобы он **не попал** в список завершённых.

Симуляция `finishedProjects()` на фикстуре:

| Шаг | Результат |
|---|---|
| Исходный список (после пропуска «мусора») | libft, ft_printf, c-piscine-shell-00, minishell, push_swap |
| Фильтр `isFinished` | libft, ft_printf, c-piscine-shell-00, push_swap (minishell выпал) |
| Даты для сортировки | libft: 2024-03-01 (marked_at); ft_printf: 2024-05-01; c-piscine-shell-00: 2024-04-01 (marked_at нет, взят updated_at); push_swap: 2024-06-01 |
| Сортировка по убыванию даты | push_swap, ft_printf, c-piscine-shell-00, libft |
| С `cursusId: 21` | push_swap, ft_printf, libft (проект бассейна с `cursus_ids: [9]` отсеян) |

Записи без даты уходят **в конец** списка.

### 5.6 Уровни: округление на входе

`roundLevel(v) = (v * 100).round() / 100`. Прогон:

| Вход | `v * 100` | `.round()` | `/ 100` |
|---|---|---|---|
| `3.4699999999999998` | `346.99999999999994` | `347` | `3.47` |
| `9.63` | около `963` | `963` | `9.63` |
| `7` (целое) | `700` | `700` | `7.0` |

Округляем **при разборе**, а не при показе, поэтому в модели хранится «чистое» число, процент считается от него, а тесты сравнивают с `3.47`, а не с длинным хвостом. Форматирование для экрана (`formatLevel`) всё равно использует `toStringAsFixed(2)`, чтобы `3.0` показывалось как `3.00`.

Альтернатива: хранить сырое число и округлять только при показе. Это сохраняет точность, но на экране и в тестах пришлось бы везде помнить про округление.

### 5.7 Процент скилла

```dart
double skillPercent(double level, {double maxLevel = maxSkillLevel})
```

Формула: `level / 20 × 100`, результат ограничен диапазоном 0–100.

- Живёт **в одной функции** и одной константе `maxSkillLevel = 20`, поэтому смена формулы это правка в одном месте.
- Защита от деления на ноль (`maxLevel <= 0` даёт 0) и от значений вне диапазона (`clamp`).
- Подтверждение формулы косвенное (масштаб радара в интре, [docs/03, раздел 11](03-api-exploration.md)). На экране формулу **подпишем**, чтобы на защите можно было ответить: «вот как мы считаем и почему».

| Уровень | Процент |
|---|---|
| 0 | 0 |
| 9.63 | 48.15 → в интерфейсе `48 %` |
| 10 | 50 |
| 20 | 100 |
| 25 (на случай, если API выйдет за максимум) | 100 |

### 5.8 Фото

Порядок: `versions.medium` → `link` → `large` → `small` → `micro`. Берётся первый **непустой https-адрес**. `http://` отвергается, потому что Android с версии 9 по умолчанию блокирует незащищённый трафик, и картинка всё равно не загрузилась бы. Если подходящего нет, `imageUrl == null`, и экран покажет заглушку.

## 7. Альтернативы и почему не они

| Подход | Суть | Почему не взяли |
|---|---|---|
| **Ручной терпимый разбор (выбрано)** | `fromJson` + функции чтения | Полный контроль над `"hidden"`, `validated?`, выбором курса; ничего лишнего в сборке; легко объяснить на защите |
| `json_serializable` | генератор кода по аннотациям | Нужен `build_runner`, сгенерированные файлы, дополнительные зависимости; плохо ложится на «`hidden` как null» и выбор курса, всё равно пришлось бы писать ручные преобразователи |
| `freezed` | неизменяемые классы, `copyWith`, равенство, объединения | Мощно, но избыточно для двух экранов; опять кодогенерация |
| `dart_mappable` | современная кодогенерация | То же: лишняя зависимость ради нескольких классов |
| Строгие касты `json['x'] as String` | минимум кода | Падают на каждой дыре в данных (см. [раздел 2.2](#22-где-ломается-наивный-разбор)) |
| Работа с `Map` напрямую | без моделей | Опечатки в ключах, логика на экранах, сложно тестировать |
| Сопоставление с образцом Dart 3 | см. ниже | Хорошо для обязательных полей, неудобно для десятков необязательных |

Пример сопоставления с образцом (Dart 3), для знакомства:

```dart
if (json case {'login': String login, 'wallet': int wallet}) {
  // здесь login и wallet уже имеют точные типы
} else {
  // структура не подошла
}
```

Если в будущем модели разрастутся, переход на `json_serializable` разумен. Тогда на защите объяснять придётся ещё и генератор.

## 8. Хорошие практики, которые здесь применены

- **Разбор на границе.** Весь JSON превращается в типы один раз, дальше им никто не оперирует.
- **Неизменяемость** (`final`, `const`).
- **Одна ответственность на функцию**: `readString` читает строки, `pickMainCursus` выбирает курс, `skillPercent` считает процент.
- **Чистые функции без побочных эффектов** легко тестировать (для них не нужны ни телефон, ни сеть).
- **Правила в одном месте**: `hidden` в `readString`, формула в `skillPercent`, статус в `isFinished`.
- **Минимизация данных**: разбираем только показываемое.
- **Тесты на «ужасные» входы**, а не только на хороший сценарий.
- **Не логировать профиль целиком**: в нём почта и (иногда) телефон.
- **Вымышленные тестовые данные.** Реальный JSON с твоей почтой в репозиторий не кладём.

## 9. Ловушки

| Ловушка | Что происходит | Как обошли |
|---|---|---|
| `7` против `7.0` | JSON не различает, `jsonDecode` отдаёт `int` или `double`; `as double` на `int` падает | `readDouble` принимает любой `num` |
| Ключ `'validated?'` | вопросительный знак часть имени, легко потерять | ключ написан в одном месте (`ProjectResult.fromJson`), а фикстура теста содержит именно этот ключ, так что опечатка вскроется |
| `Map<String, dynamic>` против `Map<dynamic, dynamic>` | проверка типа `is Map<String, dynamic>` может не пройти для «динамической» карты | `readMap` имеет второй путь через `Map<String, dynamic>.from` |
| Сравнение `double` в тестах | `0.1 + 0.2 != 0.3` | `closeTo(48.15, 1e-9)` там, где есть вычисления |
| `List.sort` не гарантирует стабильность | равные даты могут поменяться местами | в тестах не полагаемся на порядок записей с одной датой |
| `DateTime.tryParse` и часовой пояс | строка с `Z` даёт UTC | для сортировки неважно; при показе даты на экране учтём |
| Проекты с `validated? == true`, но не завершённые | если фильтровать по `validated?`, получим лишние записи | фильтр по `status`, тест на этот случай |
| Фото по `http://` | Android блокирует незащищённый трафик | только `https://` |
| Тест, который проходит всегда | создаёт ложное чувство безопасности | такой тест (проверка `toString` на «2030») я нашла и удалила |

## 13. Вопросы на защиту по этому этапу

- Как приложение ведёт себя, если какого-то поля нет в ответе? → терпимый разбор, `null` → N/A; пример: проект без `final_mark`.
- Как вы показываете скрытые данные? → `"hidden"`, пусто и `null` сводятся к `null` в `readString`, экран показывает N/A; это покрыто тестом.
- Как вы выбираете, какой курс показывать? → `slug == '42cursus'`, иначе курс с максимальным уровнем.
- Как определяете завершённость и «провален»? → `status == 'finished'`; `validated? == false` значит провален; есть реальный пример, где `validated?` и статус расходятся.
- Откуда процент скилла? → в API его нет, считаем `level / 20 × 100`; максимум 20 подтверждён масштабом радара в интре, формула подписана на экране.
- Почему не `json_serializable`? → [раздел 7](#7-альтернативы-и-почему-не-они).
- Как вы тестировали без телефона? → чистые функции и фикстура, `flutter test`.
